How to Define an Ontology

A practical guide to creating structured conceptual vocabularies

1 How to Define an Ontology

This guide shows how to create and organize ontologies (.syno) to structure your conceptual vocabulary in a systematic, auditable way.

ONTOLOGY blocks are organizing principles

ONTOLOGY blocks do not commit you to a formal ontology: they are the organizing principles of the project, and the compiler calls the whole the organizing model. The same mechanism serves a flat list of concepts, a vocabulary with synonyms, a taxonomy or a multi-relation taxonomy exported as SKOS — the degree is a research decision. The function of each field (label, definition, hierarchy, consolidation) is declared with ROLE in the template. See The Organizing Model.

Use this guide if you:

  • Need to define reusable concepts
  • Want to organize concepts into thematic groups
  • Want terminological consistency in the project

1.1 First, the Template

The fields of an ONTOLOGY block are declared in the template. The example below is used throughout this guide; the field names are yours.

ONTOLOGY FIELDS
    REQUIRED definition
    OPTIONAL group, used_for, kind_of
END ONTOLOGY FIELDS

FIELD definition TYPE TEXT
    SCOPE ONTOLOGY
    ROLE NOTE DEFINITION
    DESCRIPTION Definition of the concept and application criterion
    GUIDELINES
        Say what the concept is and when to apply it.
        Correct: Barrier linked to purchase price; excludes maintenance cost.
        Wrong: Things about money.
    END GUIDELINES
END FIELD

FIELD group TYPE TOPIC
    SCOPE ONTOLOGY
    DESCRIPTION Theme that groups the concept (a term without spaces)
END FIELD

FIELD used_for TYPE TEXT
    SCOPE ONTOLOGY
    ROLE LABEL ALTERNATIVE
    DESCRIPTION Synonyms used by the sources
END FIELD

FIELD kind_of TYPE CODE
    SCOPE ONTOLOGY
    ROLE HIERARCHY KIND
    DESCRIPTION Broader concept, when there is one
END FIELD

The ROLE lines are optional. Without them the fields are just text; with them the compiler validates labels and hierarchy.

1.2 Basic Structure

Each block defines one concept:

ONTOLOGY cost
    definition: Factors related to price, budget and economic viability
    group: adoption_barriers
END ONTOLOGY

A concept name has no spaces. Use letters (accents are accepted), digits, _ and -. Matching with the codes of the annotations ignores case.

Prefer plain names

Accented characters are allowed, but plain names are easier to type, search and use in other tools.

1.3 How to Add Concepts

ONTOLOGY cost
    definition: Factors related to price, budget and economic viability
    group: adoption_barriers
END ONTOLOGY

ONTOLOGY technical_complexity
    definition: Perceived difficulty of use or need for specialist knowledge
    group: adoption_barriers
END ONTOLOGY

1.3.1 Terminological Variants

When different sources use different terms for the same concept, keep one canonical name and record the variants as alternative labels:

ONTOLOGY organizational_resistance
    definition: Cultural or structural opposition to change
    group: contextual_factors
    used_for: institutional inertia, resistance to change
END ONTOLOGY

A label belongs to a single concept (E115). When a code used in annotations is a registered label, the compiler suggests the right concept.

1.3.2 Hierarchy (“is a kind of”)

Declare the broader concept with a ROLE HIERARCHY field:

ONTOLOGY infrastructure
    definition: Technical resources available to operate the system
    group: technology_factors
END ONTOLOGY

ONTOLOGY network_infrastructure
    definition: Network and broadband capacity
    group: technology_factors
    kind_of: infrastructure
END ONTOLOGY

The compiler requires the parent to have a block, accepts several parents and refuses cycles. There are three species of hierarchy: kind (KIND), part (PART) and instance (INSTANCE). Subtree counts appear in the JSON, the graph and the editor.

Adopted hierarchy and stated relations

What is in the .syno is what the project adopts. What sources state stays in the chains of the annotations, with evidence.

1.4 How to Group Concepts

A TOPIC field groups concepts with no predefined list: use the same value for what belongs together.

1.4.1 By Analytical Dimension

ONTOLOGY upfront_cost
    definition: Investment required to implement
    group: economic_dimension
END ONTOLOGY

ONTOLOGY staff_acceptance
    definition: Degree of staff buy-in to the change
    group: social_dimension
END ONTOLOGY

1.4.2 With Several Classifications

A template may ask for several classifications, including closed scales (ORDERED, where the index is stored):

ONTOLOGY Public_Acceptance
    topic: Social
    aspect: 10
    dimension: 1
    confidence: HIGH
    reasoning: Community and collective dynamics central to acceptance;
        co-occurs with stakeholder engagement and trust.
    description: The degree to which local communities support or oppose
        energy transition projects.
END ONTOLOGY

1.4.3 By Process Stage or Actor

ONTOLOGY awareness
    definition: Knowledge that the technology exists
    group: pre_adoption
END ONTOLOGY

ONTOLOGY satisfaction
    definition: Perception of expectations met after adoption
    group: post_adoption
END ONTOLOGY

ONTOLOGY usability
    definition: Ease of everyday operation
    group: user_perspective
END ONTOLOGY

1.5 Causal Relations

Chain relations are declared in the template (.synt), in the CHAIN field, not in the ontology. See How to Create Chains.

ITEM @source_01
    chain: high_cost -> INHIBITS -> adoption
END ITEM

1.6 Referencing Concepts in Annotations

ITEM @source_01
    quote: "The price is too high"
    code: cost
END ITEM

Every concept used in a CODE field or in a chain should exist in the ontology. A concept without a block raises a warning (summarized in one line, or detailed with --check-codes); with --strict, compilation fails.

1.7 How to Validate Your Ontology

synesis check ontology.syno                        # only the syntax of the file
synesis compile project.synp --check-codes         # consistency of the project
Message Cause Fix
Concept `X` duplicated two blocks for the same concept merge the blocks
Required field `definition` missing in ONTOLOGY block a required field is missing fill it in
Identifier `X` contains the invalid character name with a disallowed character use letters, digits, _, -
Code `X` is not defined in the organizing model code without a block create the block or fix the code
Concepts `A` and `B` have identical descriptions likely duplicate differentiate or consolidate

At the end, the compiler describes the profile of the model (flat list, vocabulary, taxonomy…). With ROLE, it also warns about concepts with no evidence and no descendant with evidence (E120).

1.8 Generating the Ontology with AI

With the corpus annotated, synesis-coder proposes definitions grounded in the use of each concept:

synesis-coder ontology --project project.synp --output ontology.syno --update

Review the result: a definition is a proposal. To produce definitions, synonyms and taxonomy in stages, declare PHASE blocks.

1.9 How to Evolve the Ontology

1.9.1 Add a Concept

  1. add the ONTOLOGY block to the .syno
  2. compile with --check-codes

1.9.2 Consolidate Two Concepts

With a ROLE USE field in the template, the deprecated name counts as the other one without editing the annotations:

FIELD use TYPE CODE
    SCOPE ONTOLOGY
    ROLE USE
END FIELD
ONTOLOGY voice_phishing
    use: vishing
END ONTOLOGY

synesis-coder consolidate project.synp voice_phishing --into vishing moves labels and parents, with a manifest, and is undone with --revert.

1.9.3 Rename a Concept

Rename the block and update the .syn files: in VS Code, F2 on the code renames it across the project. If the vocabulary has been published (SKOS), prefer USE, so that the old address keeps resolving.

1.9.4 Split a Broad Concept

ONTOLOGY acquisition_cost
    definition: Initial purchase price
    group: economic_factors
END ONTOLOGY

ONTOLOGY maintenance_cost
    definition: Recurring operating expenses
    group: economic_factors
END ONTOLOGY

Then review each annotation that used the original concept and decide which one applies. To find the occurrences, use the Codes panel in VS Code or the source_file and source_line columns of the CSV tables.

    definition: Communication with external systems

END ONTOLOGY

    group: non_functional_requirements

1.11 Documenting Decisions

Use comments in the .syno files themselves:

# DECISION 2026-02-04: we split "cost" into two concepts after
# finding ambiguity in interviews 15 to 20

ONTOLOGY operating_cost
    # NOTE: includes training, support and recurring licences
    definition: Recurring maintenance and operating expenses
    group: economic_factors
END ONTOLOGY

1.12 Several Ontology Files

For large projects, split by domain; a whole folder can be included:

ontology/
├── actors.syno
├── processes.syno
└── outcomes.syno
PROJECT my_analysis
    TEMPLATE "template.synt"
    INCLUDE BIBLIOGRAPHY "references.bib"
    INCLUDE ANNOTATIONS "annotations"
    INCLUDE ONTOLOGY "ontology"
END PROJECT

For a vocabulary shared by several projects, use INCLUDE SHARED ONTOLOGY.
