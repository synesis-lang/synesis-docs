1 Synesis: Language Reference Guide

Language 1.1 · verified with compiler synesis 0.16.0

1.1 Introduction

1.1.1 Definition

Synesis is a declarative Domain-Specific Language (DSL) for formalizing, validating and compiling analytical corpora of qualitative research. The compiler turns interpretive annotations into canonical structures, preserving both human readability and formal rigor.

1.1.2 What the Compiler Does

  • Validates the syntax and semantics of annotations
  • Builds an AST (Abstract Syntax Tree)
  • Produces structured formats: JSON, CSV, Excel, JSONL (Alpaca), OKF bundles and SKOS vocabularies
  • Validates and normalizes concepts according to configurable templates

1.1.3 What the Compiler Does NOT Do

  • It is not a runtime or execution system
  • It performs no statistical analysis
  • It manages no user interface
  • It keeps no state between runs
  • It does not create the structure of your data for you
  • It does not judge the theoretical validity of relations: it checks the form, not the reading

1.1.4 Hard Boundaries

The compiler processes text files, produces structured artifacts and exits. There is no persistent state, no conditional loops and no side effects beyond writing output files.

1.2 Installation and Command Line

Requires Python 3.10 or later.

pip install synesis
synesis --version
Compiler commands
Command What it does
synesis init creates a minimal project in the current folder
synesis compile <project.synp>… validates and compiles; with two or more projects, runs the link step
synesis export <project.synp> [block] runs the EXPORT blocks of the project
synesis check <file> checks only the syntax of one file
synesis validate-template <template.synt> checks the structure of a template
synesis help-field [TYPE] shows what a field type requires, accepts or forbids
synesis export-snippets generates editor snippets from the language rules
compile options
compile option Effect
--json <file> exports canonical JSON (schema 3.1)
--csv <folder> exports CSV tables
--xls <file> exports an Excel workbook
--alpaca <file> exports JSONL for model fine-tuning
--okf <folder> exports an OKF bundle (experimental); the folder must be new or empty
--okf-generated-at <ISO> date written into the OKF bundle (omitted by default)
--stats shows the summary and the structural profile
--check-codes lists every code without a concept in the ontology
--strict treats warnings as errors (turns on --check-codes)
--force writes the artifacts even with errors
--diagnostics-json <file> writes every diagnostic as JSON, even when there are errors

synesis export accepts --check-codes, --force and --publish (SKOS: records the published IRIs).

To look up the language from the terminal there is the synesis-help package: synesis-help lookup CHAIN, synesis-help search bundle.

1.3 Files and Formats

1.3.1 Input Files

Extension Description
.synp Project file (single entry point)
.syn Annotation files (SOURCE + ITEM)
.syno Ontology files (ONTOLOGY)
.synt Template file (FIELD definitions)
.bib BibTeX/BibLaTeX references
.toml Dataset records (INCLUDE DATASET)

.synr files (revision proposals written by synesis-coder) are not part of the project and go into no INCLUDE.

1.3.2 Output Files

Format How to generate Description
JSON --json or EXPORT JSON full representation of the project, with node locations
CSV --csv or EXPORT CSV sources, items, ontologies and chains tables
Excel --xls or EXPORT XLS the same tables as sheets
Alpaca JSONL --alpaca or EXPORT ALPACA instruction/input/output pairs
OKF --okf or EXPORT OKF folder of Markdown readable by agents (experimental)
SKOS EXPORT SKOS the organizing model in Turtle
Diagnostics --diagnostics-json errors, warnings and notices with location

1.3.3 Traceability

Every output writes paths relative to the folder of the .synp, with forward slashes. Two copies of the same project produce the same result (the JSON only differs in the export timestamp). A file outside the folder (INCLUDE SHARED) appears with ../.

Each CSV row includes location columns:

bibref,from_code,relation,to_code,source_file,source_line,source_column
'@silva2024,Cost,INHIBITS,Trust,annotations.syn,6,5

The apostrophe before @silva2024 is intentional: the compiler protects cells starting with =, +, - or @, so that a spreadsheet does not run them as formulas. Strip it when processing the CSV in another tool.

1.3.4 Compiler Invariants

  1. Deterministic compilation: the same input produces the same output
  2. Errors reported with file, line, column and context, in English
  3. Compilation with errors emits only diagnostics; nothing is exported (unless --force)
  4. Bibliographic references are validated when the project declares INCLUDE BIBLIOGRAPHY
  5. Controlled vocabulary: every code used in a CODE field or in a chain should exist as an ONTOLOGY. A code without a concept is a warning; use --strict to treat it as an error

1.4 Project Structure (.synp)

The project file orchestrates the components of the analysis and is the single entry point for the compiler.

1.4.1 Syntax

PROJECT project_name

    TEMPLATE "filename.synt"
    [INCLUDE BIBLIOGRAPHY "filename.bib"]
    [INCLUDE ANNOTATIONS "file, folder or pattern"]
    [INCLUDE ONTOLOGY "file, folder or pattern"]
    [INCLUDE SHARED ONTOLOGY "../shared/vocabulary.syno"]
    [INCLUDE DATASET "records/*.toml"]

    [METADATA
        version: 1.0
        author: string
        [created: date]
        [modified: date]
        [dataset: string]
    END METADATA]

    [DESCRIPTION
    Free text describing the project (at the same indentation as DESCRIPTION).
    END DESCRIPTION]

    [QUESTIONS
        Q1: A question the project must be able to answer
    END QUESTIONS]

    [PHASE ONTOLOGY name
        FIELDS field
    END PHASE]

    [EXPORT format name
        OUTPUT "path"
    END EXPORT]

END PROJECT

Square brackets mark optional parts; they are not part of the syntax.

1.4.2 Semantics

  • PROJECT: required keyword that starts the project definition
  • TEMPLATE: the .synt file with the validation rules (required)
  • INCLUDE: declares the files of the project. Nothing is loaded by discovery: what is not declared does not enter the analysis
  • METADATA: project metadata
  • DESCRIPTION: free description that travels with the exports. The text lines sit at the same indentation as DESCRIPTION; deeper indentation is a syntax error
  • QUESTIONS, PHASE, EXPORT: see The Organizing Model and EXPORT Blocks

The items of PROJECT must all be at the same level: either all indented or all at column 0.

1.4.3 INCLUDE: Files, Folders and Patterns

Every INCLUDE accepts a file, a folder or a glob pattern, and several lines of the same kind add up. A folder is read recursively by the extension of the kind (.bib, .syn, .syno, .toml).

PROJECT corpus
    TEMPLATE "template.synt"
    INCLUDE BIBLIOGRAPHY "Sources"
    INCLUDE BIBLIOGRAPHY "extra.bib"
    INCLUDE ANNOTATIONS "annotations_*/*.syn"
    INCLUDE ONTOLOGY "ontology"
END PROJECT
  • A .syn or .syno present in the project folder and not declared is an error (E061, E062).
  • An empty .syn or .syno, or one with comments only, is valid.
  • The same key in two .bib (or .toml) files is an error (E089).

All paths are resolved relative to the folder of the .synp. For safety, the compiler only reads files in that folder and below; a path that escapes produces E075.

1.4.4 Shared Ontology

INCLUDE SHARED ONTOLOGY is the only exception to the containment rule. It lets several projects of one study use a single conceptual vocabulary without duplicating it:

PROJECT member
    TEMPLATE "template.synt"
    INCLUDE SHARED ONTOLOGY "../shared/vocabulary.syno"
END PROJECT

The authorization lives in the declaration — the word SHARED, versioned and auditable in the .synp — not in the geometry of the path. That is why it accepts network shares (\\server\...), another drive (Z:/...) or ...

SHARED applies to ONTOLOGY only

INCLUDE SHARED BIBLIOGRAPHY or INCLUDE SHARED ANNOTATIONS produce error E084.

1.5 Template Definition (.synt)

The template defines the structure and the validation rules of annotations.

1.5.1 Template Header

TEMPLATE qualitative_analysis version: "1.0" author: "Researcher"

The header is optional. When present, the metadata goes on the same line as the name: on its own line, the template does not compile.

1.5.2 Field Blocks

Each scope has at most one block, which says which fields apply and how strictly:

SOURCE FIELDS | ITEM FIELDS | ONTOLOGY FIELDS
    [REQUIRED field [, field]]
    [OPTIONAL field [, field]]
    [FORBIDDEN field [, field]]
    [REQUIRED BUNDLE field, field [, field]]
    [OPTIONAL BUNDLE field, field [, field]]
    [REQUIRED | OPTIONAL field ON BIBLIOGRAPHY]
    [REQUIRED | OPTIONAL field ON DATASET "path.in.record"]
END SOURCE FIELDS | END ITEM FIELDS | END ONTOLOGY FIELDS

ON BIBLIOGRAPHY and ON DATASET apply only in SOURCE FIELDS, in clauses with a single field.

1.5.3 Complete Example

TEMPLATE qualitative_analysis version: "1.0" author: "Researcher"

# ============================================
# SOURCE FIELDS
# ============================================

SOURCE FIELDS
    OPTIONAL access_date
END SOURCE FIELDS

FIELD access_date TYPE DATE
    SCOPE SOURCE
    DESCRIPTION Date the source was accessed
END FIELD

# ============================================
# ITEM FIELDS
# ============================================

ITEM FIELDS
    REQUIRED quote
    REQUIRED BUNDLE note, chain
    OPTIONAL code
END ITEM FIELDS

FIELD quote TYPE QUOTATION
    SCOPE ITEM
    DESCRIPTION Textual excerpt extracted from the source
END FIELD

FIELD note TYPE MEMO
    SCOPE ITEM
    DESCRIPTION Analytical memo explaining the interpretation and the causal mechanism identified
END FIELD

FIELD code TYPE CODE
    SCOPE ITEM
    DESCRIPTION Concepts the excerpt is evidence of
END FIELD

FIELD chain TYPE CHAIN
    SCOPE ITEM
    ARITY >= 2
    DESCRIPTION Causal/relational chain between ontology concepts
    RELATIONS
        ENABLES: Necessary or facilitating condition (A allows B to happen)
        INFLUENCES: Direct causal effect (A affects or changes B)
        CONSTRAINS: Limits or restricts (A reduces the options or viability of B)
        CONTESTED-BY: Active opposition (A is contested or challenged by B)
        RELATES-TO: Generic meaningful association (A is related to B)
    END RELATIONS
END FIELD

# ============================================
# ONTOLOGY FIELDS
# ============================================

ONTOLOGY FIELDS
    REQUIRED description
    OPTIONAL topic
END ONTOLOGY FIELDS

FIELD description TYPE TEXT
    SCOPE ONTOLOGY
    DESCRIPTION Textual definition of the concept
END FIELD

FIELD topic TYPE TOPIC
    SCOPE ONTOLOGY
    DESCRIPTION Topic or thematic domain of the concept
END FIELD

Every defined field must be listed in a FIELDS block (E042), and every listed field needs a FIELD (E039) with the same scope (E006).

Comments start with #. Inside a GUIDELINES block # is not a comment: the line is part of the instruction sent to the AI.

1.6 Field Definition (FIELD)

The FIELD declaration sets the type, the scope and the constraints of each field.

1.6.1 Syntax

FIELD name TYPE type
    SCOPE SOURCE | ITEM | ONTOLOGY
    [DESCRIPTION one line of text]

    [ARITY operator number]          # CHAIN only (required)
    [RELATIONS                       # CHAIN only
        NAME: description
    END RELATIONS]

    [VALUES                          # ORDERED and ENUMERATED only (required)
        [index] value: description   # ORDERED: with [index]
        value: description           # ENUMERATED: without index
    END VALUES]

    [FORMAT [min..max]]              # SCALE only (required)

    [IDENTIFIES entity]              # SCOPE SOURCE only
    [REFERS TO entity]               # SCOPE SOURCE only

    [ROLE family [species]]          # SCOPE ONTOLOGY only

    [CONTEXT FROM DATASET "section"] # any type
    [GUIDELINES                      # any type
        Instructions for filling the field.
    END GUIDELINES]
END FIELD

1.6.2 Complete FIELD Example

FIELD chain TYPE CHAIN
    SCOPE ITEM
    DESCRIPTION Causal chain between concepts
    ARITY >= 2
    RELATIONS
        INFLUENCES: Relation of causal influence
        ENABLES: Enabling relation
        INHIBITS: Inhibiting relation
    END RELATIONS
END FIELD

FIELD aspect TYPE ORDERED
    SCOPE ONTOLOGY
    DESCRIPTION Dooyeweerd's modal aspect
    VALUES
        [1] quantitative: Numerical aspect
        [2] spatial: Spatial aspect
        [3] kinematic: Kinematic aspect
        [4] physical: Physical aspect
        [5] biotic: Biotic aspect
    END VALUES
END FIELD

FIELD sentiment TYPE ENUMERATED
    SCOPE ITEM
    DESCRIPTION Sentiment expressed in the excerpt
    VALUES
        positive: Positive sentiment
        negative: Negative sentiment
        neutral: Neutral sentiment
    END VALUES
END FIELD

FIELD confidence TYPE SCALE
    SCOPE ITEM
    DESCRIPTION Confidence level of the interpretation
    FORMAT [1..5]
END FIELD

FIELD quote TYPE QUOTATION
    SCOPE ITEM
    DESCRIPTION Textual excerpt extracted from the source
    GUIDELINES
        Extract the exact verbatim quote from the source text.
        Do not paraphrase or summarize — preserve the original wording.
        Include enough context for the quote to be self-explanatory.
        Omit only if the passage is not quotable (e.g., tables, figures).
    END GUIDELINES
END FIELD

1.6.3 GUIDELINES Block

GUIDELINES is an optional specifier accepted by any FIELD. Its content is free text with instructions on how to fill the field, addressed to AI agents or human coders. DESCRIPTION says what the field is; GUIDELINES says how to fill it well.

1.6.3.1 Purpose

GUIDELINES turns the template from a data schema into a coding protocol:

  • Per-field instruction: the AI receives specific rules for each field, reducing ambiguity
  • Traceable decisions: the rules live in the template, versioned and auditable
  • Correction loop: the AI writes Synesis blocks → the compiler validates → the errors serve as correction instructions

synesis-coder warns when a field has no GUIDELINES; with --require-guidelines the warning becomes an error.

1.6.3.2 Semantics

  • The content is free text; the compiler neither interprets nor validates it
  • Multiple lines are preserved and the inner indentation is removed
  • An empty block yields null in the JSON
  • The compiled value is exported in the "guidelines" key of each field specification in the JSON

1.6.3.3 What Works in Practice

  • Correct/Wrong pairs, one for each decision the coder will face
  • One-sentence tests (“Test: is every A a B?”)
  • Stating the unit of each value (“one status per chain”)
FIELD note TYPE MEMO
    SCOPE ITEM
    DESCRIPTION Analytical memo of the causal mechanism identified
    GUIDELINES
        Identify the causal mechanism linking the quote to the research question.
        State the mechanism in one sentence: "[Factor] [verb] [outcome] because [reason]."
        Ground the interpretation in the text — do not infer beyond what is stated.
        If causality is ambiguous, describe the relationship as associative.
    END GUIDELINES
END FIELD

1.6.4 Function of Ontology Fields: ROLE

In SCOPE ONTOLOGY fields, ROLE declares the function of the value in the organizing model: label (LABEL PREFERRED|ALTERNATIVE|HIDDEN), note (NOTE DEFINITION|USAGE|EXAMPLE|COUNTEREXAMPLE), hierarchy (HIERARCHY KIND|PART|INSTANCE) or deprecated name (USE). The full table is in The Organizing Model.

1.7 Field Types

1.7.1 Table of Types

Type Meaning Form of the value Requires
QUOTATION Textual excerpt from the source text —
MEMO Researcher’s analytical note text —
TEXT Generic free text text —
CODE Conceptual label (categorization) concepts separated by commas —
CHAIN Relation between concepts A -> B or A -> REL -> B ARITY
TOPIC Dynamic grouping a single term without spaces —
ENUMERATED Value from a closed unordered list one of the values, spelled identically VALUES
ORDERED Value from a closed ordered list the index of the option VALUES with [index]
SCALE Number within a range number FORMAT
DATE Date text (the format is not checked) —

The three scopes accept the same types. The only asymmetry is deliberate: IDENTIFIES and REFERS TO exist only in SCOPE SOURCE, and ROLE only in SCOPE ONTOLOGY. Use synesis help-field <TYPE> to see the property matrix of each type.

1.7.2 ORDERED: Store the Index

In an ORDERED field the datum is the position; the label is for display (the editor shows it next to the index).

ONTOLOGY Cost
    aspect: 4
END ONTOLOGY

Writing the label (aspect: physical) produces E088, with the index to use.

1.7.3 Language vs Template

Level FIXED (language) CONFIGURABLE (template)
Keywords SOURCE, ITEM, ONTOLOGY, FIELD, END Field names such as aspect, quote
Data types QUOTATION, MEMO, CODE, CHAIN, TEXT etc. Values in ORDERED/ENUMERATED lists
Structure SOURCE/ITEM/ONTOLOGY blocks, FIELD…END syntax Which fields are REQUIRED/OPTIONAL
Modifiers BUNDLE, REQUIRED, OPTIONAL, SCOPE, TYPE Which fields form a BUNDLE

Keywords are case-insensitive.

1.8 Structural Blocks

1.8.1 SOURCE

Unit of provenance: where the information comes from. Each SOURCE references an entry of the .bib (or a dataset record).

SOURCE @smith2023
    access_date: 2025-01-15
END SOURCE

ITEM @smith2023
    quote: "The technology shows promising results."
    note: The author expresses optimism about the results
    chain: Technology -> INFLUENCES -> Acceptance
END ITEM

The body of SOURCE is optional when the template requires no field. A @bibref cannot open two SOURCE blocks in the same file, and every ITEM needs a SOURCE with the same @bibref in the same file.

1.8.2 ITEM

The fundamental analytical unit. Holds excerpts, memos, codes and chains. Belongs to exactly one SOURCE.

ITEM @ref2025
    quote: Extracted text

    note: First interpretation
    chain: A -> INFLUENCES -> B

    note: Second interpretation
    chain: C -> ENABLES -> D
END ITEM

1.8.3 ONTOLOGY

Defines a concept of the controlled vocabulary.

ONTOLOGY Cost
    topic: Economics
    description: Economic factor representing financial expenditure
END ONTOLOGY

ONTOLOGY Public_Acceptance
    topic: Social_Factors
    description: Community-level support for technology
END ONTOLOGY

Use names without spaces (a concept with spaces cannot be cited in chains). Matching between a used code and its concept ignores case. Two blocks for the same concept are an error (E068).

1.8.4 Multi-line Values

A value can continue on the following lines, indented deeper than the field name. The two forms below are equivalent:

ITEM @smith2023
    quote: The first line of the excerpt
        and its continuation.
    note:
        A memo that starts on the next line
        and takes two lines.
END ITEM

Continuation works for text, code lists and chains. (Between versions 0.13.4 and 0.15.0 continuation lines were silently discarded; upgrade to 0.16.0 or later.)

1.9 Codes and Controlled Vocabulary

A CODE field receives one or more concepts, separated by commas or on repeated lines:

ITEM @smith2023
    quote: Text
    code: Climate_Belief, Risk_Perception
    code: Trust
END ITEM

When a code has no ONTOLOGY block, by default the compiler emits a single summary line on the .synp (E090) — useful before the ontology exists. To see each occurrence, with a suggestion of the closest concept (E004):

synesis compile project.synp --check-codes

1.10 Semantic Chains (CHAIN)

1.10.1 Qualified Chain

When the field defines RELATIONS, the chain alternates concepts and relations:

ITEM @smith2023
    chain: Climate_Belief -> INFLUENCES -> Support
    chain: A -> INFLUENCES -> B -> ENABLES -> C
END ITEM

1.10.2 Simple Chain

When the field does not define RELATIONS, there are only concepts; the relation is implicit.

ITEM @smith2023
    chain: A -> B
    chain: A -> B -> C
END ITEM

1.10.3 Arity

ARITY is required in every CHAIN field and counts concepts: ARITY >= 2 accepts one link; ARITY >= 3 requires a mediator (antecedent → mediator → outcome). The operators are >=, >, <=, < and =.

1.10.4 Concepts Without Quotes

Compound concepts take no quotes, but cannot contain spaces.

Incorrect annotation (E015):

chain: Institutional Barrier -> ENABLES -> Financial Barrier

Correct annotation:

chain: Public_Acceptance -> INFLUENCES -> CCS_Support -> ENABLES -> Deployment

A relation cannot have the same name as a concept (E014).

1.11 BUNDLE Modifier

BUNDLE defines groups of fields that form a repeatable unit of interpretation.

ITEM FIELDS
    REQUIRED quote
    REQUIRED BUNDLE note, chain
    OPTIONAL BUNDLE page, section
END ITEM FIELDS

1.11.1 Semantics

  • REQUIRED BUNDLE: at least one complete occurrence of the group
  • OPTIONAL BUNDLE: the whole group may be absent; if one member appears, all must appear
  • Members appear in equal numbers: len(field1) == len(field2)
  • Positional pairing: field1[i] relates to field2[i]
ITEM @ref2025
    quote: Text extracted from the source

    note: First interpretation
    chain: A -> INFLUENCES -> B

    note: Second interpretation
    chain: C -> ENABLES -> D
END ITEM

A missing member produces E016; unequal counts, E017; a single-field bundle, E018.

An important use is to qualify a claim: chain, status (asserted, hypothetical, negated) and justification in the same bundle, so that a hypothesis does not show up as a finding in the exports.

1.12 TOPIC Type

TOPIC defines categories that group concepts dynamically, with no predefined list in the template.

Feature ENUMERATED TOPIC
Accepted values Predefined closed list Open, dynamic
Use Controlled categorization Emergent grouping
Validation Rejects values outside the list Any term without spaces 
ONTOLOGY Cost
    topic: Economics
    description: Economic factor representing financial expenditure
END ONTOLOGY

ONTOLOGY Public_Acceptance
    topic: Social_Factors
    description: Community-level support for technology
END ONTOLOGY

1.13 Linking Projects (IDENTIFIES / REFERS TO)

Lets you triangulate heterogeneous corpora — CVs, abstracts, institutional profiles — without turning them into a single compilation unit. Each project stays independent; the link is declared in the template and resolved in an explicit command-line step.

The model is that of the C/C++ linker: each project compiles in isolation and exposes its external references; a link step (synesis compile p1.synp p2.synp) resolves the references between them and produces the aggregate.

1.13.1 The Two Modifiers

Modifier Relational role Meaning
IDENTIFIES <entity> Primary key The field identifies the entity. Each value corresponds to a single SOURCE.
REFERS TO <entity> Foreign key The field points to the entity. May repeat.

Both are exclusive to SCOPE SOURCE fields; in another scope they produce E078.

1.13.2 Syntax

The project that owns the entity declares the primary key:

# lattes.synt — the CV corpus owns the "researcher" entity
FIELD lattes_id TYPE TEXT
    SCOPE SOURCE
    DESCRIPTION Lattes identifier of the researcher
    IDENTIFIES researcher
END FIELD

Peripheral projects point to it:

# abstracts.synt — each article points to the researcher who wrote it
FIELD author_id TYPE TEXT
    SCOPE SOURCE
    DESCRIPTION Lattes identifier of the author
    REFERS TO researcher
END FIELD

The peripheral project does not name the owner, only the entity label. Adding a third corpus requires no edit to existing templates.

1.13.3 Value Origin: ON BIBLIOGRAPHY

Some identifiers are source metadata, not content that can be extracted from the text. ON BIBLIOGRAPHY declares that the value lives in the .bib entry of the SOURCE:

SOURCE FIELDS
    REQUIRED lattes_id ON BIBLIOGRAPHY
    OPTIONAL orcid ON BIBLIOGRAPHY
END SOURCE FIELDS
@misc{cv_maria,
    author    = {Silva, Maria},
    title     = {Lattes CV},
    year      = {2026},
    lattes_id = {3474000000000167}
}

The suffix is only valid in a single-field clause: REQUIRED a, b ON BIBLIOGRAPHY is a syntax error. These fields are not required in the SOURCE block; if the value is missing in the .bib, the error is E079.

1.13.4 Isolated Compilation

A project with REFERS TO compiles normally on its own. The compiler only emits notice I080:

synesis compile abstracts.synp --json abstracts.json
abstracts.synt:11:1  [INFO]  External reference `researcher` (REFERS TO in author_id) — not materialized in isolation

1.13.5 Link Step

synesis compile lattes.synp abstracts.synp --json study.json --csv out/

The link step:

  1. Compiles each member in isolation (full validation)
  2. Resolves each REFERS TO against the owning IDENTIFIES, by entity label + exact value equality
  3. Creates one edge per match (n:1 and n:n; a multivalued field creates one edge per value)
  4. Qualifies bibrefs with the member alias (abstracts:@article_a), avoiding collisions

An error in any member aborts the link step.

The compiler never merges entities

Comparison is exact equality after trimming whitespace, without case normalization. A value that would only match under normalization becomes a near-match warning (W083).

1.13.6 Aggregate Outputs

Option Behavior in the link step
--json aggregate in schema 3.1: kind: "link", entity_owners, links section with edges and orphans
--csv writes links.csv with the resolved edges
--xls here it names a folder: one .xlsx per member plus links.xlsx
--stats per-member and aggregate statistics (a shared ontology is not counted twice)
--alpaca, --okf no exporter for the aggregate: the compiler warns
--diagnostics-json not supported yet: the compiler warns
The editor never loads the aggregate

Linking is exclusive to the command line. The language server works with isolated projects, which keeps editing fast.

See the guide How to Link Independent Projects.

1.14 Forbidden Fields (FORBIDDEN)

FORBIDDEN declares, in a FIELDS block, a field of the same scope that cannot hold a value in that block. It is useful, for instance, for a derived template that keeps the definition of a field but does not want it filled in.

ITEM FIELDS
    REQUIRED quote, code
    FORBIDDEN note
END ITEM FIELDS

A block that fills in the forbidden field produces error E021: Forbidden field 'note' in ITEM block — remove this line.

1.15 Dataset Values (ON DATASET, INCLUDE DATASET, CONTEXT FROM DATASET)

Just as ON BIBLIOGRAPHY brings the value from the .bib entry, ON DATASET brings it from a TOML record, one file per record. The value is not typed in the .syn.

1.15.1 Declaring the Dataset in the Project

PROJECT interviews
    TEMPLATE "template.synt"
    INCLUDE DATASET "records/*.toml"
    INCLUDE ANNOTATIONS "annotations"
END PROJECT

1.15.2 Linking Each Record to a SOURCE

A SCOPE SOURCE field with IDENTIFIES and ON DATASET is the key of the record: the value at that TOML path must equal the bibref of the SOURCE.

SOURCE FIELDS
    REQUIRED interview ON DATASET "interview.id"
    OPTIONAL region ON DATASET "interview.region"
END SOURCE FIELDS

FIELD interview TYPE TEXT
    SCOPE SOURCE
    IDENTIFIES interview
END FIELD

FIELD region TYPE TEXT
    SCOPE SOURCE
END FIELD
# records/s1.toml — paired with SOURCE @s1
[interview]
id = "s1"
region = "Northeast"
  • The string after ON DATASET is a path inside the record (dot notation), not a file name.
  • The suffix is only valid in a single-field clause.
  • In the compiled JSON the values sit in the dataset section, indexed by bibref.
  • A REQUIRED … ON DATASET field without a value in the record produces E085.

1.15.3 Context for Coding: CONTEXT FROM DATASET

CONTEXT FROM DATASET is a property of the FIELD block, a sibling of GUIDELINES. It does not give the field a value: it names the sections of the TOML record that synesis-coder sends to the model as context when generating that field.

FIELD quote TYPE QUOTATION
    SCOPE ITEM
    CONTEXT FROM DATASET "interview"
    GUIDELINES
        Copy one to three continuous sentences, word for word.
    END GUIDELINES
END FIELD

Several sections are separated by commas: CONTEXT FROM DATASET "excerpt", "text".

1.16 EXPORT Blocks

Each EXPORT block of the .synp declares one artifact. synesis export project.synp runs all of them; synesis export project.synp json runs those of a format (or the one with that name). OUTPUT paths start at the folder of the .synp.

Format Required Optional
JSON, OKF OUTPUT GENERATED_AT
CSV, XLS OUTPUT —
ALPACA OUTPUT INSTRUCTION, MAP <fields> TO …
SKOS OUTPUT, NAMESPACE, LANGUAGE GENERATED_AT, MIN_SOURCES, ALIAS_LABEL, REGISTRY, MAP RELATIONS …

An error in a block stops only that artifact; at compile time it shows as a warning. A project error stops all of them (unless --force). The SKOS export is described in The Organizing Model.

1.16.1 Alpaca Export (EXPORT ALPACA)

EXPORT ALPACA writes a JSONL for fine-tuning language models. Each line has instruction, input and output, all three as text.

  • Without MAP or INSTRUCTION: the compiler picks built-in pairs. They do not carry the qualifier of a BUNDLE that contains a CHAIN (for instance the epistemic status), and a hypothesis comes out as an assertion. Notice I167 says so.
  • With MAP <fields> TO INSTRUCTION | INPUT | OUTPUT (synesis ≥ 0.16): the researcher declares which fields form each key.
PROJECT study
    TEMPLATE "template.synt"

    EXPORT ALPACA mechanism
        OUTPUT "out/mechanism.jsonl"
        INSTRUCTION Identify the causal relation and how the text presents it.
        MAP excerpt TO INPUT
        MAP chain, status, justification TO OUTPUT
    END EXPORT

    EXPORT ALPACA zone
        OUTPUT "out/zone.jsonl"
        INSTRUCTION Classify the rhetorical zone of the excerpt.
        MAP excerpt TO INPUT
        MAP zone TO OUTPUT
    END EXPORT
END PROJECT

One line per what. A BUNDLE in the map sets the lines: one per bundle occurrence. Fields outside it are context, repeated in full on every line of the ITEM, and never multiply lines. Without a bundle there is one line per ITEM. In the example, an ITEM with two chains yields two lines, both with the same excerpt.

Text of a key. A single field yields only the value ("Result"). Several fields yield one labelled block per field, in the order of the MAP:

chain:
lure → EXPLOITS → trust
status: Hypothetical
justification:
The author suggests the relation but does not test it.

A CHAIN enters with all its triples. A field without a value on a line is left out of the text. A line with every OUTPUT field empty is not written. Only the exact duplicate of the three keys is removed.

Dataset card. Next to the JSONL, <name>.card.json records the composition, the hashes of the .synp and the template, the counts (lines, empty, ITEMs without the bundle, duplicates), the count of each value of the ENUMERATED/ORDERED fields in OUTPUT and the fields left out.

Rules. Each rule stops only this artifact:

  • In declared mode, MAP <fields> TO OUTPUT is required (E158).
  • There is exactly one source of instruction (E159).
  • An OUTPUT field cannot also be in INPUT or INSTRUCTION (E162): the answer would leak into the prompt.
  • Fields from two bundles are refused (E163).
  • ONTOLOGY fields and SOURCE fields with ON BIBLIOGRAPHY or ON DATASET are not supported yet (E164).

Leaving a bundle qualifier (such as status) out of the map is only a notice (I166).

1.17 Compilation Pipeline

# Stage Responsibility
1 Discovery Read the .synp, resolve paths, expand folders and patterns
2 Template Read and validate the .synt
3 Bibliography and dataset Load .bib and TOML records
4 Parsing Analyse .syno and .syn files (LALR parser)
5 Transformation Convert trees into a typed AST
6 Semantic validation References, types, required fields, bundles, chains, roles
7 Linking Associate ITEMs with SOURCEs, codes and chains with the ontology; build indices
8 Export Write the requested artifacts 
Project = Template + Bibliography/Dataset + Annotations + Ontology

1.18 Diagnostics

Each problem is reported with file, line, column and a message that points to the fix:

a.syn:6:5  [ERROR]  Concept `Public Acceptance` contains spaces. Suggested fix -> `Public_Acceptance`
a.syn:4:1  [ERROR]  Bundle (note, chain) with unequal counts: note=2, chain=1

The complete catalogue, with examples, is in the Error Guide.

1.20 Appendix A: Consolidated Syntax

1.20.1 Project (.synp)

PROJECT project_name
    TEMPLATE "filename.synt"
    INCLUDE BIBLIOGRAPHY "filename.bib"
    INCLUDE ANNOTATIONS "annotations"
    INCLUDE ONTOLOGY "filename.syno"

    METADATA
        version: 1.0
        author: Research team
    END METADATA

    DESCRIPTION
    Free text describing the project.
    END DESCRIPTION

    QUESTIONS
        Q1: Which barriers are reported?
    END QUESTIONS

    EXPORT JSON
        OUTPUT "out/project.json"
    END EXPORT
END PROJECT

1.20.2 Template (.synt)

TEMPLATE name version: "1.0"

ITEM FIELDS
    REQUIRED quote
    OPTIONAL chain
END ITEM FIELDS

FIELD quote TYPE QUOTATION
    SCOPE ITEM
    DESCRIPTION Literal excerpt
END FIELD

FIELD chain TYPE CHAIN
    SCOPE ITEM
    ARITY >= 2
    RELATIONS
        ENABLES: condition that makes possible
    END RELATIONS
    GUIDELINES
        Filling instructions.
    END GUIDELINES
END FIELD

1.20.3 Annotations (.syn)

SOURCE @bibref
END SOURCE

ITEM @bibref
    quote: Excerpt from the source
    chain: A -> ENABLES -> B
END ITEM

1.20.4 Ontology (.syno)

ONTOLOGY concept_name
    description: Definition of the concept
END ONTOLOGY
