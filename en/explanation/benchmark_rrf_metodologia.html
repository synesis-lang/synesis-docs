How the Benchmark Was Run

Complete gold standard, scripts and results of the comparison between keyword search, search by meaning and fusion

What this page is

It is the methodological appendix of Vector Embeddings and GraphRAG, for those who want to audit the experiment instead of accepting the numbers. Here are the complete gold standard of 40 questions, the description of the scripts, the exact queries sent to the database and the question-by-question results.

You do not need to read this to use the feature. You need to read it to check that it does what we say.

1 Summary for the Reviewer

Corpus Social_Acceptance — 1,388 concepts on social acceptance of energy transition technologies
Database ArcadeDB 26.7.3, database social_acceptance, queried through the HTTP API
Embedding model sentence-transformers/all-mpnet-base-v2, 768 dimensions, local
Indexes FULL_TEXT (Lucene/BM25) and LSM_VECTOR (cosine, INT8 quantization)
Sample 40 concepts drawn with fixed seed 20260817
Gold standard One question per concept, frozen before any search
Depth top-10; RRF with the standard constant k = 60
Measurement date 17 August 2026
Where the numbers come from

All values on this page come from the run of 17 August 2026 against a real ArcadeDB database. The gold standard, the scripts and the raw output live in the case-studies/benchmark_rrf folder of this documentation project, which is not yet published in a public repository. The page reads the results directly from the file generated by the measurement, so the result tables and charts are not typed by hand.

2 The Design, and What It Protects Against

The central trap in any search comparison is writing the question after seeing what each method returned. Whoever does that can prove anything. The design below exists to make that impossible.

Step 3 is what gives value to steps 4 and 5: the gold standard is a separate file, written before any search.

Where this design comes from

Nothing here was invented for the occasion. The design follows the established standard for evaluation in Information Retrieval, described in Manning et al. (2008) — the canonical reference of the field, freely accessible.

  • The test collection structure (documents + information needs + relevance judgements) is that of chapter 8.2, the same as the Cranfield collection and the TREC rounds. Our equivalent: the 1,388 concepts, the 40 questions and the target concept of each.
  • Freezing the judgements before running the searches is what separates a test collection from a demonstration — the alternative (judging after seeing the output) measures the evaluator, not the system.
  • The metrics (Recall@k, MRR, nDCG) are those of chapter 8.4. The logarithmic discount of nDCG, 1/log₂(1+position), is used here exactly as defined there; with a single relevant item per question, the ideal ranking is worth 1 and DCG is already nDCG.
  • The BM25 that ArcadeDB runs is the probabilistic model of chapter 11.4.3, with frequency saturation (k₁) and document length normalization (b) — formalized in Robertson & Zaragoza (2009).
  • RRF fusion comes from Cormack et al. (2009), including the constant k = 60.

Where our design diverges from the standard, this is declared in Design limitations — above all regarding who wrote the questions and the adoption of a single answer per question.

2.1 Step 1 — the draw

Simple random sampling over the 1,388 concepts, with a fixed seed and deterministic ordering before the draw (without it, file reading order would change the sample between runs).

Full script: case-studies/benchmark_rrf/sample_concepts.py. Running it again with the same seed produces exactly the same sample.

2.2 Step 2 — the questions

For each concept drawn, one natural-language question following a single verifiable rule:

No content word of the concept name may appear in the question.

The aim is to simulate the researcher who describes the phenomenon in their own words because they did not memorize the ontology’s controlled vocabulary. The rule was checked by code, not by eye — and the check caught a real violation (Technology_Uptake × “technology”), fixed before any search ran:

2.3 Step 3 — the three searches

All run inside ArcadeDB, with no reimplementation in Python. That is the difference between measuring the product and measuring an approximation of it.

Keyword search (BM25) — FULL_TEXT index, ordered by the Lucene score:

SELECT name, $score as s FROM Chain
WHERE SEARCH_INDEX('Chain[search_name,ontology_description,reasoning,
                    rgt_element_a,rgt_element_b,theoretical_significance]',
                   '<question>') = true
ORDER BY s DESC LIMIT 10

Search by meaning — LSM_VECTOR index, nearest neighbours of the question vector:

SELECT expand(vector.neighbors('Chain[embedding]', :v, 10))

The vector :v is generated locally with the same model that embedded the corpus. Using different models on the two sides would produce meaningless neighbours — a silent failure, because the database accepts the vector and returns wrong results without complaint.

Fusion (RRF) — the standard formula of the IR (Information Retrieval, the field that studies search systems) literature, adding the two lists without normalizing scales:

Show code 
def fuse_rrf(rank_lists, k=10, RRF_K=60):
    scores = {}
    for ranking in rank_lists:
        for position, name in enumerate(ranking, start=1):
            scores[name] = scores.get(name, 0.0) + 1.0 / (RRF_K + position)
    return [n for n, _ in sorted(scores.items(), key=lambda kv: -kv[1])][:k]

The constant 60 was not tuned to favour the result: it is the value proposed in the article that introduced the method (Cormack et al., 2009), kept untuned precisely to avoid introducing one more degree of freedom. That work already showed the effect we find again here — rank fusion outperforms individual methods, including learning-to-rank methods.

1. Fusion wins on all seven metrics. That was not guaranteed: if one method were superior on its own, fusion would be cost without return. The average position of the right answer rises from 0.421 to 0.552 (+31%), and the top-10 hit rate goes from 57.5% to 87.5%.

2. Meaning alone does not dominate. For 1st place, vector search (0.325) falls below keyword search (0.350). A corpus of 1,388 concepts has many semantic neighbours, and choosing between near-synonyms is exactly where vectors hesitate.

3. The errors do not overlap — and that is what makes fusion work. Of the 40 cases, only 5 are ranked 1st by both methods; 9 only exact word ranks 1st and 8 only meaning does. That is, 17 questions are solved by exactly one of the two. Methods that failed together would have nothing to gain from fusion.

5 What Went Wrong, and Was Not Hidden

5.1 Fusion Can Lose a Target One of the Methods Found

Show code 
losses = [r for r in res["por_pergunta"]
          if r["rrf"]["rank"] is None and (r["bm25"]["rank"] or r["vector"]["rank"])]
print(f"In **{len(losses)} of the 40 questions**, the target appeared in the top-10 of a single method "
      f"but vanished from the fusion top-10:\n")
for r in losses:
    b = r["bm25"]["rank"] or "—"
    v = r["vector"]["rank"] or "—"
    print(f"- `{r['gold']}` — word: {b} · meaning: {v} · fusion: outside the top-10")

In 3 of the 40 questions, the target appeared in the top-10 of a single method but vanished from the fusion top-10:

  • Benefit — word: — · meaning: 10 · fusion: outside the top-10
  • Capital_Cost — word: — · meaning: 6 · fusion: outside the top-10
  • Energy_Transformation — word: — · meaning: 6 · fusion: outside the top-10

This is not an implementation defect: it is how RRF works. When the target is deep in only one list (6th to 10th position) and the other method contributes ten different candidates, the sum of weights pushes the target past the cut-off. It is the price of fusing without normalizing scales — and the reason fusion wins in aggregate without winning on every individual question.

5.2 Generic Concepts Are Intrinsically Ambiguous

Four sampled targets — Context, Driver, Benefit and Time — are generic labels in a corpus of 1,388 items. The question “the surrounding circumstances that frame how everything else is interpreted” legitimately matches dozens of concepts.

They were kept in the sample. Removing them after seeing that they give poor results would be exactly the contamination the frozen gold standard exists to prevent. They drag the metrics down, and that is honest.

5.3 Design Limitations

1. Whoever wrote the questions knew the answer. The 40 questions were written by a language model (Claude Opus 5) looking at the description of each concept. Even with the disjoint vocabulary rule, someone who knows the target tends to describe it in a retrievable way. This is the most serious limitation of this measurement — and the literature is explicit about it: Manning, Raghavan and Schütze recommend that information needs be designed by domain experts and warn against using random combinations of query terms as a substitute for real needs (2008, ch. 8.5). Questions collected from real researchers without access to the ontology would be more faithful — and would probably produce worse numbers.

2. One corpus, one language. Everything here is Social_Acceptance, in English, with all-mpnet-base-v2. Another language, model or conceptual density changes the numbers. Measure on your project before assuming the same gain.

3. A single answer per question. The gold standard allows only one correct concept. A good share of the “errors” are neighbours a researcher would accept in a conversation. A gold standard with multiple valid answers would give higher and more realistic numbers — at the cost of a subjective judgement about what counts as acceptable. The problem is well known: human relevance judgement is not a device that reliably reports a gold standard, being quite idiosyncratic and variable (2008, ch. 8.5), which is why reference collections usually measure inter-judge agreement (the kappa statistic) instead of assuming a single obvious gold standard.

4. Forty questions show a pattern, not a distribution. The qualitative conclusion (errors do not overlap) is robust; the decimals should not be treated as constants of the system. For calibration: the early rounds of TREC — the reference in the field — used 50 information needs each (2008, ch. 8.2). With 40, this experiment is of the same order of magnitude as established collections, but at the lower end; more questions would give more stable estimates.

6 Reproducing from Scratch

The files below belong to the case-studies/benchmark_rrf folder mentioned above, not yet published.

# 1. Start the ArcadeDB server, with the social_acceptance database loaded

# 2. Dependencies
pip install "synesis-graph[embeddings]"

# 3. Draw (rewrites sample.json — identical, the seed is fixed)
cd case-studies/benchmark_rrf
python sample_concepts.py

# 4. Measurement (rewrites results.json)
python run_benchmark.py
File Role
sample_concepts.py Step 1 — draws the 40 concepts with a fixed seed
sample.json Output of the draw, with descriptions
questions.json The frozen gold standard — 40 (question, concept) pairs
run_benchmark.py Step 3 — runs the searches and computes the metrics
results.json Measurement output — feeds all charts on this page

The searches are read-only: running the benchmark does not change the database.

What the literature corroborates, and what it does not

Corroborates: the test collection structure, the requirement to freeze judgements before measuring, the three metrics and their interpretation, the two search methods and the fusion formula. None of these elements is a local invention.

Does not corroborate — and could not: the values obtained. No reference predicts performance on a specific corpus; the result from one corpus does not transfer to another. That is why the practical recommendation remains to measure on your own project.
