1 Synesis: Ideas

Ideas: Language Extension Specification Proposals

What this document contains

This is a document of proposals — specifications that have been designed but are not yet implemented. The syntax shown in the proposals does not compile with the current compiler.

For what already works, see the Language Reference and the Grammar.

Proposals that became real

Several needs treated here as “ideas” have already been met, sometimes by a design different from the one proposed:

Original idea What exists today
Aggregating parallel projects (STUDY block / master project) Proposal discarded for overloading the editor. Independent projects linked by IDENTIFIES / REFERS TO: How to Link Independent Projects
Vocabulary shared between projects INCLUDE SHARED ONTOLOGY
Output artifacts declared in the project (RENDER command) EXPORT blocks in the .synp (JSON, CSV, XLS, Alpaca, OKF, SKOS), run with synesis export
Strict “is-a” taxonomy (TAXONOMY block) Fields with ROLE HIERARCHY in the ontology, without property inheritance
Detecting hierarchy cycles Error E118, for hierarchies declared with ROLE HIERARCHY
Concepts defined and never used Diagnostic E120, for hierarchies declared with ROLE HIERARCHY
Immediate graph visualization synesis-graph html
Data Science integration and compiler as a library synesis.load, with DataFrame output

The meaning of each code is in the Error Guide.

1.1 Introduction to the Extensions

This specification details features under consideration for a future version of the Synesis language. The focus is to evolve the language from a linear annotation system into a knowledge management system (Zettelkasten), and to introduce native support for canonical loci (sacred texts).

1.2 Canonical (Biblical/Exegetical) Annotation

An addressing system specialized for sacred texts that use the Locus pattern (Book, Chapter, Verse). To keep the grammar intact, canonical addressing would be implemented through a specific field type (TYPE PERICOPE), leaving the standard block structure untouched.

Today the same address can be recorded in a TYPE TEXT field, without format validation.

1.2.1 The PERICOPE Field Type

No block is replaced. The SOURCE block is still used to reference the bibliographic work (the specific translation or manuscript via BibTeX). The analytical unit (ITEM) receives a field typed as PERICOPE to identify the exact passage.

Syntax in the .syn file:

SOURCE @niv2011
    translation_type: Dynamic equivalence
END SOURCE

# The ITEM references the translation and gives the locus in a field
ITEM @niv2011
    passage: ROM 8:28-30, 32a
    quote: "And we know that in all things God works for the good..."
    code: Providence
END ITEM

1.2.2 Addressing Rules (Parsing)

The parser would apply strict rules to identify books, with ergonomic flexibility in verse punctuation:

  1. USX code (strict): exactly 3 capital letters for the book (e.g. MAT, GEN, ROM). Full names would not be accepted, to avoid ambiguity.
  2. Chapter separator (flexible): both colon (:) and period (.) separate chapter and verse (e.g. ROM 8:1 or ROM 8.1). The syntax tree (AST) normalizes the variation.
  3. Verses and subdivisions: hyphen - for ranges and comma , for lists, with lowercase letters attached to numbers for exegetical subdivisions (e.g. 6a, 6b).

1.2.3 Example Template for Exegesis

In the .synt file the field would be declared with type PERICOPE and scope ITEM.

TEMPLATE biblical_exegesis

ITEM FIELDS
    REQUIRED passage, quote
    OPTIONAL code
END ITEM FIELDS

FIELD passage TYPE PERICOPE
    SCOPE ITEM
    DESCRIPTION Canonical locus address (Book Chap:Verses)
END FIELD

FIELD quote TYPE QUOTATION
    SCOPE ITEM
    DESCRIPTION Textual excerpt from the bibliographic source
END FIELD

1.2.4 Implementation Notes (Lark Grammar)

Sketch of how the value of a PERICOPE field would be processed by the language rules:

// The strict rule that processes the Locus field value
pericope_value: usx_code WS INT separator verse_list

// USX codes (strictly 3 capital letters)
usx_code: UCASE_LETTER~3

// The separator (accepts both common academic formats)
separator: ":" | "."

// Verse list with commas and optional spaces
verse_list: verse_node ("," WS? verse_node)*

// A node may be a single verse or a range
verse_node: verse_single | verse_single "-" verse_single

// The verse: a number followed by an optional lowercase letter (e.g. 6a)
verse_single: INT /[a-z]?/

1.2.5 Estimated Impact of the Change

In the compiler:

  • Template parser: add PERICOPE to the list of field types, alongside TEXT, QUOTATION, MEMO, CHAIN etc.
  • Lark grammar: create the pericope_value rule.
  • Transformer (Python): split the string into a dictionary (book, chapter, verses).

The relation between ITEM and SOURCE, BibTeX validation and BUNDLE validation would not change; exporters would treat the new field like any field defined in the template.

In the VS Code extension:

  • Syntax highlighting: a regular expression for the canonical pattern (e.g. \b[A-Z]{3}\s\d+[:.]\d+[\d\-,a-z\s]*\b).
  • Snippets: autocomplete the ITEM block with the locus field already in place.
  • Code Actions (optional): convert “Romans 8, 1 to 3” into ROM 8:1-3 as a quick-fix suggestion, without touching the compiler.

1.4 Strategies for Comparative Exegesis

Synesis offers structural flexibility to researchers who need to compare manuscripts or translations of the same passage. Since an ITEM belongs to exactly one SOURCE, there are two approaches, depending on how the data will be used later. The examples use the proposed PERICOPE type; today, declare these fields as TEXT.

1.4.1 Approach 1: the Relational “Join” (multiple ITEMs)

Prioritizes bibliographic rigour. Each base text (e.g. the Greek original and an English translation) is treated as a separate work in a SOURCE block. The annotation blocks correlate because the locus field acts as a relationship key.

SOURCE @na28
    language: "grc"
END SOURCE

ITEM @na28
    passage: ROM 8:1
    quote: "Οὐδὲν ἄρα νῦν κατάκριμα..."
END ITEM

SOURCE @niv2011
    language: "en"
END SOURCE

ITEM @niv2011
    passage: ROM 8:1
    quote: "Therefore, there is now no condemnation..."
END ITEM

Analytical advantage: produces normalized flat tables suited to Data Science workflows — translations can be grouped in Python (Pandas) or queried in graph databases, connecting nodes through the locus property.

1.4.2 Approach 2: Direct Comparison with BUNDLE (single item)

If the focus is visual and hermeneutical juxtaposition, and the base text is an interlinear or parallel Bible, use the BUNDLE modifier, which guarantees positional correspondence between version and excerpt.

In the template (.synt):

ITEM FIELDS
    REQUIRED passage
    REQUIRED BUNDLE version, quote  # Fields tied by position
END ITEM FIELDS

FIELD passage TYPE PERICOPE
    SCOPE ITEM
    DESCRIPTION Canonical address
END FIELD

FIELD version TYPE ENUMERATED
    SCOPE ITEM
    DESCRIPTION Abbreviation of the bibliographic translation
    VALUES
        NA28: Nestle-Aland (Greek)
        NIV: New International Version
        ESV: English Standard Version
    END VALUES
END FIELD

FIELD quote TYPE QUOTATION
    SCOPE ITEM
    DESCRIPTION Excerpt matching the version
END FIELD

In the annotation (.syn):

ITEM @interlinear_bible2025
    passage: ROM 8:1

    # -- Bundle pair 1 --
    version: NA28
    quote: "Οὐδὲν ἄρα νῦν κατάκριμα..."

    # -- Bundle pair 2 --
    version: NIV
    quote: "Therefore, there is now no condemnation..."
END ITEM

Analytical advantage: keeps the comparison cohesive in one block. The compiler raises an error if a version is annotated without its excerpt, or the reverse, and ENUMERATED accepts only the versions declared in VALUES.

1.5 Legal and Normative Annotation (Domain Extension)

The Synesis ecosystem is agnostic about the research domain. Configurable field types allow modelling the complexity of legal texts (legislation and case law) without changing the SOURCE and ITEM block structure.

1.5.1 1. Topographic Addressing (legislation)

Normative texts require structured, non-linear addressing.

  • Suggested field type: TYPE LEGAL_LOCUS
  • Parser behaviour: capture and structure the topography of the law (act, article, paragraph, item, sub-item). Example target syntax (Brazilian law): CF/88 Art. 5, inc. X.

1.5.2 2. Case Law Ontology

Court decisions have strict categories, which can already be enforced today with ENUMERATED.

  • Common categories: Ratio Decidendi (main thesis), Obiter Dictum (side remark) and Headnote (official summary).

1.5.3 3. Precedent Networks (CHAIN)

Mapping how decisions relate over time can use qualified chains (CHAIN). The proposal adds the use of bibliographic references as chain nodes.

1.5.4 Proposed Example (template and annotation)

TEMPLATE legal_analysis

ITEM FIELDS
    REQUIRED locus, quote
    OPTIONAL legal_concept, chain
END ITEM FIELDS

FIELD locus TYPE LEGAL_LOCUS
    SCOPE ITEM
    DESCRIPTION Normative or case-law topographic address
END FIELD

FIELD legal_concept TYPE ENUMERATED
    SCOPE ITEM
    DESCRIPTION Structural classification of the court decision
    VALUES
        RATIO: Ratio Decidendi (main thesis)
        OBITER: Obiter Dictum (side argument)
        HEADNOTE: Official summary
    END VALUES
END FIELD

FIELD chain TYPE CHAIN
    SCOPE ITEM
    ARITY >= 2
    RELATIONS
        OVERRULES: A higher court overturns the previous thesis
        CITES_PRECEDENT: Decision grounded in a previous case
        DISTINGUISHES: Current case distinguished from the general rule
    END RELATIONS
END FIELD
SOURCE @stj_petition_1234
    access_date: 2026-02-17
END SOURCE

ITEM @stj_petition_1234
    locus: CF/88 Art. 5, inc. X
    legal_concept: RATIO
    quote: "intimacy, private life, honor and image of persons are inviolable..."

    # Precedent graph between bibliographic works (rulings)
    chain: @stj_petition_1234 -> OVERRULES -> @tj_decision_999
END ITEM

Expected advantage: exported to relational (CSV) or graph formats, the project would give the researcher the precedent network with its legal topology and traceability to the text.

For the modelling that already works today, see Synesis for Legal Professionals.

1.6 Knowledge Management (Zettelkasten)

Introduces “Permanent Notes” that synthesize knowledge. To preserve the language invariants, the Zettelkasten would not be a new block but a set of specialized fields inside the ITEM.

1.6.1 The Zettelkasten as a SOURCE

Since every ITEM belongs to a SOURCE, a BibTeX entry representing the author’s note repository is recommended (e.g. @zettel_vault).

# The "Source" is the researcher's own repository
SOURCE @zettel_vault
    access_date: 2026-02-17
END SOURCE

# The ITEM acts as the Permanent Note (Zettel)
ITEM @zettel_vault
    zettel_id: 2026011401
    title: "The Principle of Atomicity"
    body: "A DSL should force concepts to be broken down..."

    # Explicit connections
    links: 2026011205, 2025123001

    # Metadata and traceability
    topic: DSL_Design
    origin: @turing1936
END ITEM

1.6.2 Proposed Field Types

New types would support the graph topology of a Zettelkasten, with cross-validation at the linking stage:

  • ZETTEL_ID: unique note identifier (usually a timestamp); the compiler would guarantee there are no duplicate IDs.
  • ZETTEL_LINK: creates directed edges between notes; the compiler would check that referenced IDs exist.
  • BIB_REF: references an external source directly in the field, creating a citation edge.
TEMPLATE zettel_knowledge_base

ITEM FIELDS
    REQUIRED zettel_id, title, body
    OPTIONAL links, topic, origin
END ITEM FIELDS

FIELD zettel_id TYPE ZETTEL_ID
    SCOPE ITEM
    DESCRIPTION Unique chronological identifier of the Zettel
END FIELD

FIELD links TYPE ZETTEL_LINK
    SCOPE ITEM
    DESCRIPTION Connections to other Zettels (comma-separated IDs)
END FIELD

FIELD origin TYPE BIB_REF
    SCOPE ITEM
    DESCRIPTION Bibliographic reference that inspired the permanent note
END FIELD

1.6.3 Implementation Notes (Lark Grammar)

// The generic field rule absorbs the new types
field_value: text_value
           | chain_value
           | zettel_id_value
           | zettel_link_value
           | bib_ref_value

// The ID is a strictly numeric string (e.g. YYYYMMDDHH)
zettel_id_value: INT

// Comma-separated list of IDs
zettel_link_value: INT ("," WS? INT)*

// Citation format with '@'
bib_ref_value: "@" LCASE_LETTER+ DIGIT+

1.6.4 Impact on Export

With zettel_link and bib_ref as ITEM field types, the JSON export would carry clean lists of links and the BibTeX key in origin, enough to build the note network in a graph database.

1.7 Detecting Ontological Redundancy

The compiler would scan the ontology for concepts with similar spelling, preventing fragmentation of the knowledge graph. Today part of this need is met in assisted coding, by the normalize command of synesis-coder.

  • Algorithm: Levenshtein / Jaro-Winkler distance.
  • Behaviour: warning during compilation.
  • Detection example: SocialInteraction vs Social_Interaction.

1.8 New Structural Commands

1.8.1 CONSTRAINT (business rules)

Logical invariants to ensure the methodological consistency of annotations.

CONSTRAINT
    # Mutual exclusion: an item cannot have both codes at once
    FORBID Code "Sentiment: Positive" WITH Code "Risk: Critical"

    # Logical dependency: code B requires code A
    REQUIRE Code "Solution" IF Code "Problem" PRESENT
END CONSTRAINT

1.8.2 CROSSREF (citation network)

Formalizes rhetorical relations between bibliographic sources, independently of internal annotations.

CROSSREF
    @smith2019 -> REFUTES -> @doe2018
    @jones2020 -> EXTENDS -> @smith2019
END CROSSREF
