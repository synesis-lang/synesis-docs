Como Ligar Projetos Independentes

Triangular corpora heterogêneos com IDENTIFIES e REFERS TO

1 Como Ligar Projetos Independentes

Este guia mostra como conectar dois ou mais projetos Synesis que descrevem as mesmas entidades a partir de fontes diferentes — currículos e artigos, entrevistas e documentos institucionais, perfis e publicações.

Você deve usar este guia se:

  • Tem corpora separados que se referem às mesmas pessoas, organizações ou processos
  • Quer cruzar esses corpora sem fundi-los num único projeto gigante
  • Precisa que cada corpus continue compilando rápido e sendo editado de forma independente
  • Quer compartilhar um único vocabulário conceitual entre vários projetos
O que este guia não faz

A ligação não funde projetos nem cria um “projeto mestre”. Cada .synp continua sendo uma unidade de compilação autônoma. A ligação é resolvida num passo explícito na linha de comando e nunca é carregada pelo editor.

2 O problema

Imagine um estudo com dois corpora:

  • lattes.synp — currículos de pesquisadores, um SOURCE por pesquisador
  • abstracts.synp — artigos científicos, um SOURCE por artigo

Cada artigo tem um autor que também tem currículo. Você quer perguntar: quais conceitos aparecem nos artigos dos pesquisadores que declararam determinada linha de pesquisa?

Três caminhos ruins e por que foram descartados:

Tentativa Por que não funciona
Juntar tudo num .synp só O editor passa a recompilar o estudo inteiro a cada gravação.
Reconciliar por identidade (A é B) Só modela 1:1. Muitos artigos → um pesquisador não é identidade, é relação.
O corpus central nomear cada periférico Adicionar um terceiro corpus exigiria editar o template do central.

A solução adotada é o modelo do linker de C/C++: cada projeto compila isolado e expõe suas referências externas; um passo de ligação resolve as referências entre eles.

3 Passo 1: declarar quem é dono da entidade

Escolha o corpus proprietário da entidade — aquele em que cada valor identifica um registro único. No exemplo, o currículo: cada pesquisador tem exatamente um.

No template lattes.synt, marque o campo identificador com IDENTIFIES:

FIELD lattes_id TYPE TEXT
    SCOPE SOURCE
    DESCRIPTION Identificador Lattes do pesquisador
    IDENTIFIES researcher
END FIELD

researcher é o rótulo da entidade, um nome que você escolhe. É por ele que os outros projetos se referem a essa entidade, sem nunca nomear o arquivo lattes.synp.

IDENTIFIES é uma chave primária

Cada valor deve corresponder a um único SOURCE. Dois SOURCEs com o mesmo valor produzem o erro E077 já na compilação isolada do projeto.

3.1 Quando o identificador vive no .bib

Identificadores como ID Lattes, ORCID ou CNPJ costumam ser metadados da fonte, não algo extraído do texto. Declare a origem com ON BIBLIOGRAPHY:

SOURCE FIELDS
    REQUIRED lattes_id ON BIBLIOGRAPHY
END SOURCE FIELDS
@misc{curriculo_maria,
    author    = {Silva, Maria},
    title     = {Currículo Lattes},
    year      = {2026},
    lattes_id = {ID-0001}
}

Para registros estruturados em TOML, o equivalente é ON DATASET.

4 Passo 2: apontar para a entidade

Nos templates dos corpora periféricos, declare o campo que aponta para a entidade com REFERS TO:

# abstracts.synt
FIELD autor_id TYPE TEXT
    SCOPE SOURCE
    DESCRIPTION Identificador Lattes do autor do artigo
    REFERS TO researcher
END FIELD

Não há menção a lattes.synp, caminho de arquivo ou ordem de compilação: o projeto periférico conhece apenas o rótulo researcher. Por isso, adicionar um quarto corpus não exige tocar em nenhum template existente.

Cardinalidade livre

REFERS TO pode repetir. Vários artigos apontando para o mesmo pesquisador (n:1) é o caso normal. Um campo multivalorado, como um artigo com vários autores, gera uma aresta por valor (n:n).

4.1 Os dois modificadores lado a lado

Modificador Papel Cria nó no grafo? Valor repete?
IDENTIFIES <entidade> Chave primária Sim Não
REFERS TO <entidade> Chave estrangeira Não Sim

Ambos só valem em campos SCOPE SOURCE (E078).

5 Passo 3: compartilhar a ontologia (opcional)

Para que os corpora usem o mesmo vocabulário, coloque a ontologia numa pasta comum e declare-a com INCLUDE SHARED ONTOLOGY:

estudo/
├── compartilhado/
│   └── vocabulario.syno
├── lattes/
│   ├── lattes.synp
│   └── lattes.synt
└── abstracts/
    ├── abstracts.synp
    └── abstracts.synt
PROJECT Lattes
    TEMPLATE "lattes.synt"
    INCLUDE BIBLIOGRAPHY "curriculos.bib"
    INCLUDE ANNOTATIONS "anotacoes/*.syn"
    INCLUDE SHARED ONTOLOGY "../compartilhado/vocabulario.syno"
END PROJECT

Cada membro fica na sua própria pasta: um .syn presente na pasta de um projeto e não incluído por ele é erro.

A palavra SHARED autoriza um alvo fora da pasta do projeto. Sem ela, ../compartilhado/... seria recusado (E075). Funciona também com pastas de rede e outros drives:

PROJECT Exemplo
    TEMPLATE "t.synt"
    INCLUDE SHARED ONTOLOGY "\\servidor\equipe\vocabulario.syno"
    INCLUDE SHARED ONTOLOGY "Z:/estudo/vocabulario.syno"
END PROJECT
SHARED só vale para ONTOLOGY

Com outro tipo, o erro é E084.

6 Passo 4: compilar isolado

Cada projeto continua compilando sozinho:

synesis compile abstracts/abstracts.synp
abstracts.synt:10:1  [INFO]  External reference `researcher` (REFERS TO in autor_id) — not materialized in isolation

É um informativo, não erro nem aviso: uma referência externa não resolvida na compilação isolada é o comportamento esperado.

7 Passo 5: ligar os projetos

Passe dois ou mais projetos ao mesmo comando:

synesis compile lattes/lattes.synp abstracts/abstracts.synp
SYNESIS v0.16.0 — Linking projects.
  compiling lattes …
  compiling abstracts …

✓ 2 projects linked. 1 edge(s) resolved ['researcher'].
⚠ 2 orphan REFERS TO value(s) (no matching IDENTIFIES).

Links between projects:

              ────IDENTIFIES────  ─────REFERS TO─────
  ENTITY      PROJECT  FIELD      PROJECT    FIELD
  researcher  lattes   lattes_id  abstracts  autor_id

Link resolution:

  abstracts (autor_id)  ->  researcher     1 resolved    2 orphans  (33%)

O que aconteceu:

  1. Cada membro foi compilado isoladamente, com validação completa (um erro em qualquer um aborta a ligação)
  2. Cada REFERS TO researcher foi comparado com o IDENTIFIES researcher
  3. Cada casamento virou uma aresta do agregado

As duas tabelas ajudam a diagnosticar: a primeira mostra o que os templates declaram; a segunda, quanto se resolveu. Um projeto ainda sem fontes aparece como aguardando coleta.

8 Entendendo os resultados

8.1 Bibrefs qualificados

No agregado, cada bibref é prefixado pelo alias do projeto de origem (lattes:@curriculo_maria). Dois corpora podem ter a mesma chave .bib sem serem confundidos.

8.2 Referências órfãs

Um valor de REFERS TO sem IDENTIFIES correspondente vira aviso (W083):

<link>:0:0  [WARNING]  Orphan REFERS TO `ID-9999` (researcher) in abstracts

Isso costuma ser legítimo — um artigo citando um autor sem currículo no corpus. Nenhum nó é criado para o órfão.

8.3 Quase-casamentos

Quando o valor casaria apenas ignorando maiúsculas e minúsculas:

<link>:0:0  [WARNING]  Orphan REFERS TO `id-0001` (researcher) — near match `ID-0001` (differs only in case)
Por que o compilador não normaliza sozinho

Normalizar fundiria entidades que a fonte pode considerar distintas. O compilador detecta e sugere, mas nunca funde. Corrija o valor na fonte, e a decisão fica registrada.

9 Erros comuns

Erro Causa Solução
E081 dois projetos declaram IDENTIFIES do mesmo rótulo só um é dono; os outros usam REFERS TO
E082 campos da mesma entidade com TYPE diferentes use o mesmo tipo
E079 campo ON BIBLIOGRAPHY ausente na entrada .bib acrescente-o à entrada

10 O grafo multiprojeto

Os backends de banco do synesis-graph transformam cada identidade em nó:

synesis-graph arcadedb-embedded \
  --project lattes/lattes.synp --project abstracts/abstracts.synp \
  --database estudo

Veja synesis-graph.

11 Por que o editor nunca carrega o agregado

A ligação é exclusiva da linha de comando. O servidor de linguagem trabalha com projetos isolados; assim, um estudo com vários corpora grandes edita tão rápido quanto um projeto pequeno. As arestas são um resultado de análise, produzido quando você compila o conjunto.

A ontologia compartilhada é vista pelo editor

Uma ontologia declarada com INCLUDE SHARED ONTOLOGY é carregada pelo editor, com autocompletar e validação, e uma mudança no arquivo externo dispara a revalidação dos projetos que o incluem. Veja A Interface LSP.
