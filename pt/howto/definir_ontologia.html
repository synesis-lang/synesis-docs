Como Definir uma Ontologia

Guia prático para criar vocabulários conceituais estruturados

1 Como Definir uma Ontologia

Este guia mostra como criar e organizar ontologias (.syno) para estruturar seu vocabulário conceitual de forma sistemática e auditável.

Blocos ONTOLOGY são princípios organizadores

Os blocos ONTOLOGY não obrigam a uma ontologia formal: são os princípios organizadores do projeto, e o compilador chama o conjunto de modelo organizador. O mesmo mecanismo serve a uma lista plana de conceitos, a um vocabulário com sinônimos, a uma taxonomia ou a uma taxonomia multirrelacional exportada em SKOS — o grau é decisão da pesquisa. A função de cada campo (rótulo, definição, hierarquia, consolidação) é declarada com ROLE no template. Ver O Modelo Organizador.

Você deve usar este guia se:

  • Precisa definir conceitos reutilizáveis
  • Quer organizar conceitos por grupos temáticos
  • Quer garantir consistência terminológica no projeto

1.1 Primeiro, o Template

Os campos de um bloco ONTOLOGY são declarados no template. O exemplo abaixo é usado neste guia; os nomes dos campos são seus.

ONTOLOGY FIELDS
    REQUIRED descricao
    OPTIONAL grupo, usado_por, tipo_de
END ONTOLOGY FIELDS

FIELD descricao TYPE TEXT
    SCOPE ONTOLOGY
    ROLE NOTE DEFINITION
    DESCRIPTION Definição do conceito e critério de aplicação
    GUIDELINES
        Diga o que o conceito é e quando aplicá-lo.
        Correto: Barreira ligada ao preço de aquisição; não inclui custo de manutenção.
        Errado: Coisas sobre dinheiro.
    END GUIDELINES
END FIELD

FIELD grupo TYPE TOPIC
    SCOPE ONTOLOGY
    DESCRIPTION Tema que agrupa o conceito (um termo sem espaços)
END FIELD

FIELD usado_por TYPE TEXT
    SCOPE ONTOLOGY
    ROLE LABEL ALTERNATIVE
    DESCRIPTION Sinônimos usados pelas fontes
END FIELD

FIELD tipo_de TYPE CODE
    SCOPE ONTOLOGY
    ROLE HIERARCHY KIND
    DESCRIPTION Conceito mais amplo, quando houver
END FIELD

As linhas ROLE são opcionais. Sem elas, os campos são apenas texto; com elas, o compilador valida rótulos e hierarquia.

1.2 Estrutura Básica

Cada bloco define um único conceito:

ONTOLOGY custo
    descricao: Fatores relacionados a preço, orçamento e viabilidade econômica
    grupo: barreiras_a_adocao
END ONTOLOGY

O nome do conceito não tem espaços. Use letras (acentos são aceitos), números, _ e -. A comparação com os códigos das anotações ignora maiúsculas e minúsculas.

Evite acentos nos nomes

Acentos são permitidos, mas nomes sem acento são mais fáceis de digitar, de buscar e de usar em outras ferramentas.

1.3 Como Adicionar Conceitos

ONTOLOGY custo
    descricao: Fatores relacionados a preço, orçamento e viabilidade econômica
    grupo: barreiras_a_adocao
END ONTOLOGY

ONTOLOGY complexidade_tecnica
    descricao: Percepção de dificuldade de uso ou necessidade de conhecimento especializado
    grupo: barreiras_a_adocao
END ONTOLOGY

1.3.1 Variações terminológicas

Quando fontes diferentes usam termos diferentes para o mesmo conceito, mantenha um nome canônico e registre as variantes como rótulos alternativos:

ONTOLOGY resistencia_organizacional
    descricao: Oposição cultural ou estrutural à mudança
    grupo: fatores_contextuais
    usado_por: inércia institucional, resistência à mudança
END ONTOLOGY

Um rótulo pertence a um só conceito (E115). Quando um código usado nas anotações é um rótulo registrado, o compilador sugere o conceito correto.

1.3.2 Hierarquia (“é um tipo de”)

Declare o conceito mais amplo com um campo ROLE HIERARCHY:

ONTOLOGY infraestrutura
    descricao: Recursos técnicos disponíveis para operar o sistema
    grupo: fatores_tecnologicos
END ONTOLOGY

ONTOLOGY infraestrutura_de_rede
    descricao: Capacidade de rede e banda larga
    grupo: fatores_tecnologicos
    tipo_de: infraestrutura
END ONTOLOGY

O compilador exige que o pai tenha um bloco, aceita vários pais e recusa ciclos. Há três espécies de hierarquia: tipo (KIND), parte (PART) e caso (INSTANCE). As contagens por subárvore aparecem no JSON, no grafo e no editor.

Hierarquia adotada e relações afirmadas

O que está no .syno é o que o projeto adota. O que as fontes afirmam continua nas cadeias das anotações, com evidência.

1.4 Como Organizar Conceitos por Grupos

Um campo TOPIC agrupa conceitos sem lista prévia: use os mesmos valores para o que deve ficar junto.

1.4.1 Por dimensão analítica

ONTOLOGY custo_inicial
    descricao: Investimento necessário para implementar
    grupo: dimensao_economica
END ONTOLOGY

ONTOLOGY aceitacao_da_equipe
    descricao: Grau de adesão dos colaboradores à mudança
    grupo: dimensao_social
END ONTOLOGY

1.4.2 Com várias classificações

Um template pode pedir várias classificações, inclusive escalas fechadas (ORDERED, em que se grava o índice):

ONTOLOGY Public_Acceptance
    topic: Social
    aspect: 10
    dimension: 1
    confidence: HIGH
    reasoning: Community and collective dynamics central to acceptance;
        co-occurs with stakeholder engagement and trust.
    description: The degree to which local communities support or oppose
        energy transition projects.
END ONTOLOGY

1.4.3 Por fase do processo ou por ator

ONTOLOGY conscientizacao
    descricao: Conhecimento sobre a existência da tecnologia
    grupo: pre_adocao
END ONTOLOGY

ONTOLOGY satisfacao
    descricao: Percepção de expectativas atendidas depois da adoção
    grupo: pos_adocao
END ONTOLOGY

ONTOLOGY usabilidade
    descricao: Facilidade de operação cotidiana
    grupo: perspectiva_usuarios
END ONTOLOGY

1.5 Relações Causais

As relações das cadeias são declaradas no template (.synt), no campo CHAIN, não na ontologia. Veja Como Criar Chains.

ITEM @fonte_01
    chain: custo_alto -> INIBE -> adocao
END ITEM

1.6 Como Referenciar Conceitos nas Anotações

ITEM @fonte_01
    quote: "O preço é muito alto"
    code: custo
END ITEM

Todo conceito usado em um campo CODE ou em uma cadeia deve existir na ontologia. Um conceito sem bloco gera um aviso (resumido em uma linha, ou detalhado com --check-codes); com --strict, a compilação falha.

1.7 Como Validar Sua Ontologia

synesis check ontologia.syno                      # só a escrita do arquivo
synesis compile projeto.synp --check-codes        # consistência do projeto
Mensagem Causa Solução
Concept `X` duplicated dois blocos para o mesmo conceito una os blocos
Required field `descricao` missing in ONTOLOGY block falta um campo obrigatório preencha o campo
Identifier `X` contains the invalid character nome com caractere não permitido use letras, números, _, -
Code `X` is not defined in the organizing model código sem bloco crie o bloco ou corrija o código
Concepts `A` and `B` have identical descriptions provável duplicata diferencie ou consolide

Ao final, o compilador descreve o perfil do modelo (lista plana, vocabulário, taxonomia…). Com ROLE, ele avisa também sobre conceitos sem evidência nem descendente com evidência (E120).

1.8 Como Gerar a Ontologia com IA

Com o corpus anotado, o synesis-coder propõe definições fundamentadas no uso de cada conceito:

synesis-coder ontology --project projeto.synp --output ontologia.syno --update

Revise o resultado: a definição é uma proposta. Para produzir definições, sinônimos e taxonomia em etapas, declare blocos PHASE.

1.9 Como Evoluir a Ontologia

1.9.1 Adicionar um conceito

  1. acrescente o bloco ONTOLOGY ao .syno
  2. compile com --check-codes

1.9.2 Consolidar dois conceitos

Com um campo ROLE USE no template, o nome preterido passa a valer pelo outro sem editar as anotações:

FIELD usar TYPE CODE
    SCOPE ONTOLOGY
    ROLE USE
END FIELD
ONTOLOGY voice_phishing
    usar: vishing
END ONTOLOGY

synesis-coder consolidate projeto.synp voice_phishing --into vishing faz a transferência de rótulos e pais, com manifesto, e se desfaz com --revert.

1.9.3 Renomear um conceito

Renomeie o bloco e atualize os .syn: no VS Code, F2 sobre o código renomeia em todo o projeto. Se o vocabulário já foi publicado (SKOS), prefira USE, para que o endereço antigo continue resolvendo.

1.9.4 Dividir um conceito amplo

ONTOLOGY custo_de_aquisicao
    descricao: Preço de compra inicial
    grupo: fatores_economicos
END ONTOLOGY

ONTOLOGY custo_de_manutencao
    descricao: Despesas recorrentes de operação
    grupo: fatores_economicos
END ONTOLOGY

Depois, revise cada anotação que usava o conceito original e decida qual se aplica. Para localizar as ocorrências, use o painel Codes do VS Code ou as colunas source_file e source_line das tabelas CSV.

1.10 Exemplos por Área

1.10.1 Análise temática

ONTOLOGY experiencia_vivida
    descricao: Relatos diretos de vivências pessoais
    grupo: temas_descritivos
END ONTOLOGY

ONTOLOGY contradicao_aparente
    descricao: Tensão entre perspectivas sobre o mesmo fenômeno
    grupo: temas_analiticos
END ONTOLOGY

1.10.2 Políticas públicas

ONTOLOGY implementador
    descricao: Agente responsável por executar a política
    grupo: atores
END ONTOLOGY

ONTOLOGY equidade
    descricao: Distribuição justa dos benefícios entre grupos
    grupo: dimensoes_de_avaliacao
END ONTOLOGY

1.10.3 Engenharia de requisitos

ONTOLOGY integracao
    descricao: Comunicação com sistemas externos
    grupo: requisitos_funcionais
END ONTOLOGY

ONTOLOGY seguranca
    descricao: Proteção de dados e autenticação
    grupo: requisitos_nao_funcionais
END ONTOLOGY

1.11 Como Documentar Decisões

Use comentários nos próprios arquivos .syno:

# DECISÃO 2026-02-04: separamos "custo" em dois conceitos após
# identificar ambiguidade nas entrevistas 15 a 20

ONTOLOGY custo_operacional
    # NOTA: inclui treinamento, suporte e licenças recorrentes
    descricao: Despesas recorrentes de manutenção e operação
    grupo: fatores_economicos
END ONTOLOGY

1.12 Vários Arquivos de Ontologia

Para projetos grandes, divida por domínio; uma pasta inteira pode ser incluída:

ontologia/
├── atores.syno
├── processos.syno
└── resultados.syno
PROJECT minha_analise
    TEMPLATE "template.synt"
    INCLUDE BIBLIOGRAPHY "references.bib"
    INCLUDE ANNOTATIONS "anotacoes"
    INCLUDE ONTOLOGY "ontologia"
END PROJECT

Para um vocabulário comum a vários projetos, use INCLUDE SHARED ONTOLOGY.
