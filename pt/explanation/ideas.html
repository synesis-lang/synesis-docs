1 Synesis: Ideias

Ideias: Propostas de especificação de Extensões da Linguagem

O que está neste documento

Este é um documento de propostas — especificações desenhadas, mas ainda não implementadas. A sintaxe mostrada nas propostas não compila no compilador atual.

Para o que já funciona, veja a Referência da Linguagem e a Gramática.

Propostas que saíram do papel

Várias necessidades tratadas aqui como “ideias” já foram atendidas, às vezes por um desenho diferente do proposto:

Ideia original O que existe hoje
Agregação de projetos paralelos (bloco STUDY / master project) Proposta descartada por sobrecarregar o editor. Projetos independentes ligados por IDENTIFIES / REFERS TO: Como Ligar Projetos Independentes
Vocabulário compartilhado entre projetos INCLUDE SHARED ONTOLOGY
Artefatos de saída declarados no projeto (comando RENDER) Blocos EXPORT no .synp (JSON, CSV, XLS, Alpaca, OKF, SKOS), executados com synesis export
Taxonomia rígida “é-um” (bloco TAXONOMY) Campos com ROLE HIERARCHY na ontologia, sem herança de propriedades
Detecção de ciclos hierárquicos Erro E118, para hierarquias declaradas com ROLE HIERARCHY
Conceitos definidos e nunca usados Diagnóstico E120, para hierarquias declaradas com ROLE HIERARCHY
Visualização imediata do grafo synesis-graph html
Integração com Data Science e compilador como biblioteca synesis.load, com saída em DataFrames

O significado de cada código está no Guia de Erros.

1.1 Introdução às Extensões

Esta especificação detalha recursos considerados para uma versão futura da linguagem Synesis. O foco é evoluir a linguagem de um sistema de anotação linear para um sistema de gestão de conhecimento (Zettelkasten), além de introduzir suporte nativo a loci canônicos (textos sagrados).

1.2 Anotação Canônica (Bíblica/Exegética)

Sistema de endereçamento especializado para textos sagrados que utilizam o padrão Locus (Livro, Capítulo, Versículo). Para manter a integridade da gramática, o endereçamento canônico seria implementado através de um tipo de campo específico (TYPE PERICOPE), mantendo intacta a estrutura padrão de blocos analíticos.

Hoje o mesmo endereço pode ser registrado num campo TYPE TEXT, sem a validação do formato.

1.2.1 Tipo de Campo PERICOPE

Não há substituição de blocos. O bloco SOURCE continua sendo utilizado para referenciar a obra bibliográfica (a Tradução ou o Manuscrito específico via BibTeX). A unidade analítica (ITEM) recebe um campo tipado como PERICOPE para identificar a passagem exata.

Sintaxe no arquivo .syn:

SOURCE @ara1993
    translation_type: Formal equivalence
END SOURCE

# O bloco ITEM referencia a tradução e especifica o locus no campo
ITEM @ara1993
    passage: ROM 8:28-30, 32a
    quote: "Sabemos que todas as coisas cooperam para o bem..."
    code: Providência
END ITEM

1.2.2 Regras de Endereçamento (Parsing)

O parser aplicaria regras estritas para a identificação dos livros, com flexibilidade ergonômica na pontuação dos versículos:

  1. Código USX (Estrito): exatamente 3 letras maiúsculas para o livro (ex: MAT, GEN, ROM). Nomes por extenso não seriam aceitos, para evitar ambiguidades.
  2. Separador de Capítulo (Flexível): tanto dois-pontos (:) quanto ponto (.) separam capítulo e versículo (ex: ROM 8:1 ou ROM 8.1). A árvore sintática (AST) normaliza a variação.
  3. Versículos e Subdivisões: hífen - para intervalos e vírgula , para listas, com letras minúsculas anexadas aos números para subdivisões exegéticas (ex: 6a, 6b).

1.2.3 Exemplo de Template para Exegese

No arquivo .synt, o campo seria declarado com o tipo PERICOPE e escopo ITEM.

TEMPLATE biblical_exegesis

ITEM FIELDS
    REQUIRED passage, quote
    OPTIONAL code
END ITEM FIELDS

FIELD passage TYPE PERICOPE
    SCOPE ITEM
    DESCRIPTION Endereçamento Locus canônico (Livro Cap:Versos)
END FIELD

FIELD quote TYPE QUOTATION
    SCOPE ITEM
    DESCRIPTION Excerto textual extraído da fonte bibliográfica
END FIELD

1.2.4 Notas de Implementação (Lark Grammar)

Esboço do processamento do valor de um campo PERICOPE nas regras da linguagem:

// A regra rigorosa que processa o valor do campo Locus
pericope_value: usx_code WS INT separator verse_list

// Códigos USX (3 letras maiúsculas estritas)
usx_code: UCASE_LETTER~3

// O separador (aceita os dois formatos acadêmicos comuns)
separator: ":" | "."

// Lista de versículos com suporte a vírgulas e espaços opcionais
verse_list: verse_node ("," WS? verse_node)*

// Um nó pode ser um versículo isolado ou um intervalo
verse_node: verse_single | verse_single "-" verse_single

// O versículo: um número seguido de uma letra minúscula opcional (ex: 6a)
verse_single: INT /[a-z]?/

1.2.5 Impacto estimado da mudança

No compilador:

  • Template Parser: acrescentar PERICOPE à lista de tipos de campo, ao lado de TEXT, QUOTATION, MEMO, CHAIN etc.
  • Lark Grammar: criar a regra pericope_value.
  • Transformer (Python): desmembrar a string em um dicionário (book, chapter, verses).

A relação entre ITEM e SOURCE, a validação de BibTeX e a validação de BUNDLE não mudariam; os exportadores tratariam o novo campo como qualquer campo definido no template.

Na extensão para VS Code:

  • Realce de sintaxe: uma expressão regular para o padrão canônico (ex: \b[A-Z]{3}\s\d+[:.]\d+[\d\-,a-z\s]*\b).
  • Snippets: autocompletar o bloco ITEM já com o campo de locus.
  • Code Actions (opcional): converter “Romanos 8, 1 a 3” em ROM 8:1-3 como sugestão de correção rápida, sem tocar no compilador.

1.4 Estratégias para Exegese Comparativa

A linguagem Synesis oferece flexibilidade estrutural para quem precisa comparar manuscritos ou traduções de uma mesma passagem. Como um bloco ITEM pertence a exatamente um SOURCE, há duas abordagens, conforme o uso posterior dos dados. Os exemplos usam o tipo proposto PERICOPE; hoje, declare esses campos como TEXT.

1.4.1 Abordagem 1: o “Join” Relacional (múltiplos ITEMs)

Prioriza o rigor bibliográfico. Cada texto base (ex: grego original e tradução em português) é tratado como uma obra separada no bloco SOURCE. A correlação entre os blocos de anotação ocorre porque o campo de locus atua como chave de relacionamento.

SOURCE @na28
    language: "grc"
END SOURCE

ITEM @na28
    passage: ROM 8:1
    quote: "Οὐδὲν ἄρα νῦν κατάκριμα..."
END ITEM

SOURCE @ara1993
    language: "pt-BR"
END SOURCE

ITEM @ara1993
    passage: ROM 8:1
    quote: "Agora, pois, já nenhuma condenação há..."
END ITEM

Vantagem analítica: gera tabelas planas normalizadas, adequadas a fluxos de Data Science — permite agrupar as traduções em Python (Pandas) ou fazer consultas em bancos de grafos, conectando os nós pela propriedade de locus.

1.4.2 Abordagem 2: comparação direta com BUNDLE (item único)

Se o foco é a justaposição visual e hermenêutica, e o texto-base é uma Bíblia interlinear ou paralela, usa-se o modificador BUNDLE, que garante a correspondência posicional entre a versão e o excerto.

No template (.synt):

ITEM FIELDS
    REQUIRED passage
    REQUIRED BUNDLE version, quote  # Campos atrelados posicionalmente
END ITEM FIELDS

FIELD passage TYPE PERICOPE
    SCOPE ITEM
    DESCRIPTION Endereçamento canônico
END FIELD

FIELD version TYPE ENUMERATED
    SCOPE ITEM
    DESCRIPTION Sigla da tradução bibliográfica
    VALUES
        NA28: Nestle-Aland (Grego)
        ARA: Almeida Rev. Atualizada
        NVI: Nova Versão Internacional
    END VALUES
END FIELD

FIELD quote TYPE QUOTATION
    SCOPE ITEM
    DESCRIPTION Excerto correspondente à versão
END FIELD

Na anotação (.syn):

ITEM @biblia_interlinear2025
    passage: ROM 8:1

    # -- Par 1 do Bundle --
    version: NA28
    quote: "Οὐδὲν ἄρα νῦν κατάκριμα..."

    # -- Par 2 do Bundle --
    version: ARA
    quote: "Agora, pois, já nenhuma condenação há..."
END ITEM

Vantagem analítica: mantém a comparação coesa no mesmo bloco. O compilador emite erro se uma versão for anotada sem o excerto correspondente, ou o contrário, e ENUMERATED aceita apenas as versões declaradas em VALUES.

1.5 Anotação Jurídica e Normativa (Extensão de Domínio)

O ecossistema Synesis é agnóstico em relação ao domínio de pesquisa. Tipos de campo configuráveis permitem modelar a complexidade de textos jurídicos (legislação e jurisprudência) sem alterar a estrutura de blocos SOURCE e ITEM.

1.5.1 1. Endereçamento topográfico (legislação)

Textos normativos exigem um endereçamento estruturado e não linear.

  • Tipo de campo sugerido: TYPE LEGAL_LOCUS
  • Comportamento do parser: capturar e estruturar a topografia da lei (lei, artigo, parágrafo, inciso, alínea). Exemplo de sintaxe alvo: CF/88 Art. 5, inc. X.

1.5.2 2. Ontologia jurisprudencial

Decisões judiciais têm categorias estritas, que já podem ser garantidas hoje com ENUMERATED.

  • Categorias comuns: Ratio Decidendi (tese principal), Obiter Dictum (comentário marginal) e Ementa (resumo oficial).

1.5.3 3. Redes de precedentes (CHAIN)

O mapeamento de como decisões se relacionam ao longo do tempo pode usar cadeias qualificadas (CHAIN). A proposta acrescenta o uso de referências bibliográficas como nós da cadeia.

1.5.4 Exemplo proposto (template e anotação)

TEMPLATE legal_analysis

ITEM FIELDS
    REQUIRED locus, quote
    OPTIONAL legal_concept, chain
END ITEM FIELDS

FIELD locus TYPE LEGAL_LOCUS
    SCOPE ITEM
    DESCRIPTION Endereço topográfico normativo ou jurisprudencial
END FIELD

FIELD legal_concept TYPE ENUMERATED
    SCOPE ITEM
    DESCRIPTION Classificação estrutural da decisão judicial
    VALUES
        RATIO: Ratio Decidendi (Tese principal)
        OBITER: Obiter Dictum (Argumento marginal)
        EMENTA: Resumo oficial
    END VALUES
END FIELD

FIELD chain TYPE CHAIN
    SCOPE ITEM
    ARITY >= 2
    RELATIONS
        OVERRULES: Tribunal superior derruba a tese anterior
        CITES_PRECEDENT: Decisão baseia-se em caso passado
        DISTINGUISHES: Distinção do caso atual em relação à regra geral
    END RELATIONS
END FIELD
SOURCE @stj_peticao_1234
    access_date: 2026-02-17
END SOURCE

ITEM @stj_peticao_1234
    locus: CF/88 Art. 5, inc. X
    legal_concept: RATIO
    quote: "são invioláveis a intimidade, a vida privada, a honra e a imagem..."

    # Grafo de precedentes entre obras bibliográficas (acórdãos)
    chain: @stj_peticao_1234 -> OVERRULES -> @tj_decisao_999
END ITEM

Vantagem esperada: exportado para formatos relacionais (CSV) ou grafos, o projeto daria ao pesquisador a rede de precedentes com sua topologia legal e rastreabilidade até o texto.

Para a modelagem que já funciona hoje, veja Synesis para Profissionais do Direito.

1.6 Gestão de Conhecimento (Zettelkasten)

Introduz a criação de “Notas Permanentes” que sintetizam conhecimento. Para preservar as invariantes da linguagem, o Zettelkasten não seria um novo bloco, mas um conjunto de campos especializados dentro do ITEM.

1.6.1 O Zettelkasten como SOURCE

Como cada ITEM pertence a um SOURCE, recomenda-se uma entrada BibTeX que represente o repositório de notas do autor (ex: @zettel_vault).

# A "Fonte" é o próprio repositório do pesquisador
SOURCE @zettel_vault
    access_date: 2026-02-17
END SOURCE

# O ITEM atua como a Nota Permanente (Zettel)
ITEM @zettel_vault
    zettel_id: 2026011401
    title: "O Princípio da Atomicidade"
    body: "Uma DSL deve forçar a quebra de conceitos..."

    # Conexões explícitas
    links: 2026011205, 2025123001

    # Metadados e rastreabilidade
    topic: DSL_Design
    origin: @turing1936
END ITEM

1.6.2 Tipos de campo propostos

Novos tipos suportariam a topologia de grafo de um Zettelkasten, com validação cruzada na etapa de linkagem:

  • ZETTEL_ID: identificador único da nota (em geral, um carimbo de data e hora); o compilador garantiria que não há IDs duplicados.
  • ZETTEL_LINK: cria arestas direcionais entre notas; o compilador verificaria se os IDs referenciados existem.
  • BIB_REF: referencia uma fonte externa diretamente no campo, criando uma aresta de citação.
TEMPLATE zettel_knowledge_base

ITEM FIELDS
    REQUIRED zettel_id, title, body
    OPTIONAL links, topic, origin
END ITEM FIELDS

FIELD zettel_id TYPE ZETTEL_ID
    SCOPE ITEM
    DESCRIPTION Identificador cronológico único do Zettel
END FIELD

FIELD links TYPE ZETTEL_LINK
    SCOPE ITEM
    DESCRIPTION Lista de conexões para outros Zettels (IDs separados por vírgula)
END FIELD

FIELD origin TYPE BIB_REF
    SCOPE ITEM
    DESCRIPTION Referência bibliográfica que inspirou a nota permanente
END FIELD

1.6.3 Notas de Implementação (Lark Grammar)

// A regra de campo genérica absorve os novos tipos
field_value: text_value
           | chain_value
           | zettel_id_value
           | zettel_link_value
           | bib_ref_value

// O ID é uma sequência estritamente numérica (ex: YYYYMMDDHH)
zettel_id_value: INT

// Lista de IDs separados por vírgula
zettel_link_value: INT ("," WS? INT)*

// Formato de citação com '@'
bib_ref_value: "@" LCASE_LETTER+ DIGIT+

1.6.4 Impacto na exportação

Com zettel_link e bib_ref como tipos de campo do ITEM, a exportação em JSON teria listas limpas de links e a chave BibTeX em origin, o bastante para montar a rede de notas num banco de grafos.

1.7 Detecção de Redundância Ontológica

O compilador analisaria a ontologia em busca de conceitos com grafia similar, prevenindo a fragmentação do grafo de conhecimento. Hoje, parte dessa necessidade é atendida na codificação assistida, pelo comando normalize do synesis-coder.

  • Algoritmo: distância de Levenshtein / Jaro-Winkler.
  • Comportamento: aviso durante a compilação.
  • Exemplo de detecção: InteracaoSocial vs Interacao_Social.

1.8 Novos Comandos Estruturais

1.8.1 CONSTRAINT (regras de negócio)

Invariantes lógicas para garantir a consistência metodológica das anotações.

CONSTRAINT
    # Exclusão mútua: um item não pode ter ambos os códigos simultaneamente
    FORBID Code "Sentimento: Positivo" WITH Code "Risco: Crítico"

    # Dependência lógica: o código B exige a presença do código A
    REQUIRE Code "Solução" IF Code "Problema" PRESENT
END CONSTRAINT

1.8.2 CROSSREF (rede de citações)

Formaliza relações retóricas entre fontes bibliográficas, independentemente de anotações internas.

CROSSREF
    @smith2019 -> REFUTES -> @doe2018
    @jones2020 -> EXTENDS -> @smith2019
END CROSSREF
